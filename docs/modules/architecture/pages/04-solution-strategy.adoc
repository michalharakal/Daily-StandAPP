[IMPORTANT]
====
**Doc status (2026-04-30):** the `skainet-transformers` `JavaAgentLoop` + `JavaTool` tool-calling pattern described in this page was rolled back during validation. Llama 3.2 1B Q8_0 could not reliably emit the tool-call JSON the Llama 3 chat template requires. The SKAINET runtime path now uses `KLlamaSession.generate()` directly with a manually-formatted Llama 3 turn prompt; the CLI pre-fetches commits via JGit. Tool-calling references in this page are aspirational, not the current shape. See plan `continue-with-general-effort-groovy-coral.md` §V3 + §V7.2.
====

== 4.1 Technology Decisions

[cols="1,2,3"]
|===
|Decision |Choice |Rationale

|*Language*
|Kotlin 2.2+ Multiplatform
|Type-safe, concise, cross-platform support with expect/actual pattern

|*Build System*
|Gradle with Kotlin DSL
|First-class Kotlin Multiplatform support, version catalogs

|*Git Library*
|Eclipse JGit
|Pure Java, no native dependencies, mature and stable

|*LLM Engine*
|SKaiNET 0.21.0 + SKaiNET-transformers 0.21.1
|Pure Kotlin, no Python/native deps, SIMD via Vector API. The `skainet-transformers` agent loop adds tool calling on top of the kllama runtime.

|*LLM Inference Pattern*
|Agent loop with tool calling
|`JavaAgentLoop` drives a multi-turn conversation: the model emits `<tool_call>` blocks, the loop dispatches to registered `JavaTool` implementations, and the loop terminates on a plain assistant message. Replaces the previous single-shot `session.generate(prompt)` path.

|*Protocol*
|Model Context Protocol (MCP)
|Standard for AI assistant integration, supported by Claude. Note: the *MCP* tools (consumed by external assistants) and the *agent-loop* tools (consumed by our own embedded LLM) are now distinct surfaces with the same JGit backend.

|*Model Format*
|GGUF (Llama 3.2 1B Instruct, Q8_0)
|~1.3 GB embedded as a JAR resource so the CLI runs self-contained — no `MCP_LLM_MODEL_PATH` required, no external download at install time.

|*Distribution*
|Self-contained shadow JAR (`StandAPP-cli/build/libs/standapp-*-all.jar`)
|`com.gradleup.shadow` packages all dependencies plus the embedded GGUF into a single ~2.0 GB JAR. `mergeServiceFiles()` preserves SKaiNET 0.21's `KernelProvider` SPI registrations.
|===

== 4.3 Key Design Decisions

=== Decision 1: Privacy-First Local AI (Non-Negotiable)

*Problem*: Git commits contain highly sensitive information - code changes, project names, business logic, author identities. Sending this data to cloud AI services is unacceptable for many organizations and individuals.

*Solution*: Embedded LLM inference using SKaiNET kllama, running entirely on the local machine. **No cloud AI services. No exceptions.**

*Why this matters*:
* Commit messages may reference security vulnerabilities, customer names, internal projects
* Code diffs reveal proprietary algorithms and business logic
* Author information is personally identifiable data (PII)
* Many enterprises prohibit sending code to external services

*Consequences*:
* (+) **Complete privacy** - zero data leaves the machine
* (+) Works offline after initial setup
* (+) Compliant with strict enterprise security policies
* (-) Requires JDK 21+ for Vector API
* (-) One-time model download required (~4GB for 7B models)

=== Decision 2: Pluggable LLM Architecture with SKaiNET-transformers Agent Loop

*Problem*: Need local LLM inference that can dynamically pull data (git history) instead of relying on a pre-built prompt, while keeping the option to fall back to a remote endpoint for development.

*Solution*: Define `LLMService` interface for pluggable backends. Two backends, selectable via `MCP_LLM_BACKEND` environment variable (default: `SKAINET`):

* **SKAINET** (default) — `skainet-transformers` `JavaAgentLoop` over the kllama runtime, with three `JavaTool` implementations exposed to the model: `get_current_date`, `get_commits_by_author`, `get_all_commits`. Runs the embedded Llama 3.2 1B Instruct (Q8_0).
* **REST_API** — OpenAI-compatible HTTP endpoint (Ollama, llama.cpp server, LM Studio, etc.). Uses the legacy single-shot prompt path because remote tool calling is not wired through this wrapper.

*Consequences*:
* (+) Tool calling — the LLM fetches its own commit data, no PromptBuilder churn
* (+) Self-contained shadow JAR — model embedded, no env vars needed
* (+) Pure JVM, BOM-managed deps, no native library management
* (-) Requires JDK 21+ for Panama Vector
* (-) Fat JAR is large (~2.0 GB) — see Risks §11

=== Decision 3: MCP Protocol for AI Integration

*Problem*: Need to integrate with AI assistants like Claude.

*Solution*: Implement MCP server with stdio transport, exposing git tools.

*Benefits*:
* Standard protocol supported by major AI assistants
* Structured tool definitions with JSON schemas
* Bidirectional communication
