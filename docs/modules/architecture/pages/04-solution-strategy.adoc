== 4.1 Technology Decisions

[cols="1,2,3"]
|===
|Decision |Choice |Rationale

|*Language*
|Kotlin 2.4 Multiplatform
|Type-safe, concise, cross-platform support with expect/actual pattern. Follows the SKaiNET upstream toolchain (2.4.10).

|*Build System*
|Gradle 9.6 with Kotlin DSL, JDK 25 toolchain
|First-class Kotlin Multiplatform support, version catalogs. The foojay toolchain resolver provisions JDK 25 on a JDK 21+ host; `../SKaiNET-transformers` is a composite build only behind `-PuseLocalTransformers=true`.

|*Git Library*
|Eclipse JGit
|Pure Java, no native dependencies, mature and stable

|*LLM Engine*
|SKaiNET 0.53.0 core + SKaiNET-transformers 0.53.0 (Maven Central, BOM-managed)
|Pure Kotlin model definitions with SIMD via the Vector API, plus optional native FFM kernels (`skainet-backend-native-cpu`, bundled `libskainet_kernels.so`) for packed Q8_0 / Q4_K weights. `skainet-transformers` supplies the GGUF decoder loader, the Llama and Qwen network loaders, the chat templates and the `AgentLoop`.

|*LLM Inference Pattern*
|Two-model pipeline as a SKaiNET `DataPipeline`
|Qwen3-0.6B turns the request into one `get_recent_commits` tool call (structured input); Llama-3.2-3B-Instruct writes the summary. The flow is declared with the app DSL `standupFlow { … }`; every step is a `sk.ainet.data.source.PipelineStage`, so tools, transforms and generation stages can be swapped without touching the built-ins.

|*Protocol*
|Model Context Protocol (MCP)
|Standard for AI assistant integration, supported by Claude. The *MCP* tools (consumed by external assistants) and the *Qwen* tool (consumed by our own local model) are distinct surfaces over the same JGit backend.

|*Model Format*
|GGUF, downloaded on first run
|`Qwen3-0.6B-Q8_0.gguf` (~0.6 GB, `hf://Qwen/Qwen3-0.6B-GGUF`) and `Llama-3.2-3B-Instruct-Q4_K_M.gguf` (~2.0 GB, `hf://bartowski/Llama-3.2-3B-Instruct-GGUF`) are resolved through SKaiNET's `hf://` data-source resolver into `STANDAPP_MODEL_CACHE_DIR` (default `~/.cache/standapp/models`) and reused afterwards. Local files or other URIs can be supplied per model.

|*Distribution*
|Shadow JAR (`StandAPP-cli/build/libs/standapp-1.0-SNAPSHOT-all.jar`, ~20 MB)
|`com.gradleup.shadow` packages all dependencies; no model is embedded. `mergeServiceFiles()` plus an explicit re-merge of the two `META-INF/services/sk.ainet.backend.api.kernel.*` files keeps the kernel-provider SPI intact.
|===

=== The pipeline as code

[source,kotlin]
----
// JVM (jvmMain) — the standup flow is a SKaiNET DataPipeline<StandupRequest, PipelineResult>.
val models = ModelProvider.releasing()            // load / use / close each model in turn
val flow = standupFlow(models) {
    commits = qwenToolCall()                       // Qwen3-0.6B calls get_recent_commits (or gitCommits())
    preprocess { shortIds(7); firstMessageLine(120); limit(60) }
    prompt { type = PromptType.SUMMARY }
    summarize(llama())                             // Llama-3.2-3B-Instruct (or llmService(RestApiLLMService(...)))
    postprocess { parseSummary(); score(); retryOnInvalid(2) }
    onToken = { print(it) }
}
println(flow.describe())
// qwen-commits -> require-commits -> preprocess -> summarize[prompt -> llama -> parse x2]
val result = flow.execute(StandupRequest(repoDir = ".", days = 7))
----

`standapp-ai-engine` (common Kotlin) owns the vocabulary — `PreprocessBuilder`,
`PromptSpec`/`PromptBuilder`, `SummaryParser`, `QualityScorer`, `PostprocessSpec` —
and stays free of any inference dependency; the JVM stages in `llm` reuse it.

== 4.3 Key Design Decisions

=== Decision 1: Privacy-First Local AI (Non-Negotiable)

*Problem*: Git commits contain highly sensitive information - code changes, project names, business logic, author identities. Sending this data to cloud AI services is unacceptable for many organizations and individuals.

*Solution*: In-process LLM inference with SKaiNET, running entirely on the local machine. **No cloud AI services. No exceptions.** The only network access is the one-time model download (Hugging Face, via the `hf://` resolver); `STANDAPP_OFFLINE=1` forbids even that and fails fast on a cold cache.

*Why this matters*:
* Commit messages may reference security vulnerabilities, customer names, internal projects
* Code diffs reveal proprietary algorithms and business logic
* Author information is personally identifiable data (PII)
* Many enterprises prohibit sending code to external services

*Consequences*:
* (+) **Complete privacy** - no commit data leaves the machine
* (+) Works offline after the first-run download (~2.7 GB)
* (+) Compliant with strict enterprise security policies
* (-) Requires the JDK 25 toolchain (Vector API preview + FFM native access)
* (-) First run needs network access or pre-provisioned GGUF files (`STANDAPP_QWEN_MODEL_PATH`, `STANDAPP_LLAMA_MODEL_PATH`)

=== Decision 2: Two-Model Pipeline on SKaiNET 0.53

*Problem*: A single small model cannot both reliably emit a well-formed tool call and write a good summary (see the retired 1B experiments in xref:09-architecture-decisions.adoc[ADR-010/011]). We still want the model — not hand-written glue — to turn the user's request into the git query, while keeping the REST fallback for development.

*Solution*: Split the work across two models wired as a SKaiNET `DataPipeline`, selected via `MCP_LLM_BACKEND` / `--backend` (default: `SKAINET`):

* **SKAINET** (default) — `QwenCommitsStage` runs `sk.ainet.apps.kllama.chat.AgentLoop` on Qwen3-0.6B with `QwenChatTemplate(enableThinking = false)`, exactly one tool round, greedy sampling and batched prefill. `RecordingGitCommitsTool` executes `get_recent_commits(days, author?)` and records the structured `List<GitInfo>`; Qwen's prose is discarded. `LlamaGenerateStage` renders system + user through `Llama3ChatTemplate` and calls `generateUntilStop` on Llama-3.2-3B-Instruct Q4_K_M. If Qwen produces no valid call the stage logs `[STAGE/FALLBACK]` and fetches the commits directly, so the CLI always delivers a summary.
* **REST_API** — OpenAI-compatible HTTP endpoint (Ollama, llama.cpp server, LM Studio, etc.). Commits are fetched directly (`GitCommitsStage`); the same prompt/parse/score stages run around `LLMServiceGenerateStage`.

*Consequences*:
* (+) The model, not the CLI, decides the git query — and the tool guarantees a structured result
* (+) Each stage is a plain `PipelineStage`: extra tools (`qwenToolCall(tools = …)`), custom `transform`/`finish` stages and alternative generators plug in through the DSL
* (+) 3B summariser writes noticeably better standups than the retired 1B model; Q4_K_M keeps it at ~2 GB
* (+) ~20 MB JAR, models cached once per machine
* (-) First run downloads ~2.7 GB; a cold offline cache fails (exit code 4)
* (-) Two model loads per run (peak memory stays at one model with `ModelProvider.releasing()`; `--keep-models` trades memory for speed)
* (-) CPU-only decode is ~0.3 s/token for the 3B model on a 2019 laptop; the Qwen round adds ~40 s — see Risks §11

=== Decision 3: MCP Protocol for AI Integration

*Problem*: Need to integrate with AI assistants like Claude.

*Solution*: Implement MCP server with stdio transport, exposing git tools.

*Benefits*:
* Standard protocol supported by major AI assistants
* Structured tool definitions with JSON schemas
* Bidirectional communication

== 4.4 Quality Strategy

[cols="1,3"]
|===
|Quality Goal |Strategy

|*Privacy*
|Local execution only; the sole network access is the first-run model download (disable with `STANDAPP_OFFLINE=1`)

|*Performance*
|Packed, memory-mapped GGUF weights on native FFM row-major kernels; SIMD via the Java Vector API; batched prefill; KV cache capped at a 4096-token window

|*Portability*
|Kotlin Multiplatform with expect/actual for platform-specific code; inference-free `standapp-ai-engine` in common code

|*Maintainability*
|Clean module boundaries, pipeline stages as the unit of composition, dependency injection via factory functions
|===
