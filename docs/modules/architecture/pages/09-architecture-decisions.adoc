== ADR-001: Privacy-First Architecture (Foundational)

=== Status
Accepted (Non-negotiable)

=== Context
Git commits contain highly sensitive information:

* Code changes revealing proprietary algorithms
* Commit messages referencing security issues, customer names, internal projects
* Author information (PII)
* Project structure and business logic

Many developers and enterprises cannot send this data to cloud services.

=== Decision
**All AI processing must run locally. No data leaves the machine.**

This is the foundational architectural constraint that drives all other decisions.

=== Consequences
* (+) Complete privacy - zero external data transmission
* (+) Compliant with enterprise security policies
* (+) Works offline
* (+) No vendor lock-in or API costs
* (-) Requires local compute resources
* (-) Model download needed for first use

== ADR-002: Kotlin Multiplatform for Cross-Platform Support

=== Status
Accepted

=== Context
The application needs to run on multiple platforms (desktop, potentially mobile) while sharing business logic.

=== Decision
Use Kotlin Multiplatform with expect/actual pattern for platform-specific implementations.

=== Consequences
* (+) Single codebase for shared logic
* (+) Type-safe platform abstraction
* (+) Native performance on each platform
* (-) Some platforms have stub implementations only
* (-) Build complexity with multiple source sets

== ADR-003: Pluggable LLM Architecture with SKaiNET kllama

=== Status
Accepted

=== Context
Need local LLM inference without cloud dependencies. Options considered:
* llama.cpp (C++ with JNI bindings)
* JLama (Pure Java)
* SKaiNET kllama (Pure Kotlin)

=== Decision
Define `LLMService` interface for pluggable LLM backends. Use `LLMServiceFactory` to instantiate backends based on the `MCP_LLM_BACKEND` environment variable.

=== Current Implementations
* **SKaiNET kllama** (`SKaiNetLLMService`) - Pure Kotlin, GGUF model loading, SIMD via Vector API
* **REST API** (`RestApiLLMService`) - OpenAI-compatible HTTP endpoints (Ollama, llama.cpp server, LM Studio, vLLM)
* **JLama** (`JLamaService`) - Pure Java LLM inference

=== Rationale
* Pluggable architecture enables comparing multiple backends
* SKaiNET: Pure Kotlin, no native dependencies, SIMD acceleration via Java Vector API
* REST API: Leverage existing local inference servers
* JLama: Pure Java alternative for environments where Kotlin is not preferred

=== Consequences
* (+) Three production backends available
* (+) Benchmark module can compare backends side-by-side
* (+) No native library management with SKaiNET/JLama
* (+) REST API allows using Ollama and other local servers
* (-) Requires JDK 21+ for Vector API (SKaiNET)

== ADR-004: MCP Protocol for AI Assistant Integration

=== Status
Accepted

=== Context
Need to integrate with AI assistants like Claude for intelligent standup preparation.

=== Decision
Implement Model Context Protocol (MCP) server using the official Kotlin SDK.

=== Rationale
* Standard protocol supported by Anthropic
* Structured tool definitions
* JSON-RPC over stdio is simple and secure
* No network exposure required

=== Consequences
* (+) Direct integration with Claude Desktop
* (+) Standardized tool schema definitions
* (+) Secure - no network ports opened
* (-) Limited to stdio transport currently
* (-) Requires Claude Desktop configuration

== ADR-005: Eclipse JGit for Git Operations

=== Status
Accepted

=== Context
Need to read git commit history from local repositories.

=== Decision
Use Eclipse JGit library for all git operations.

=== Rationale
* Pure Java - no native git installation required
* Mature and well-tested
* Full git protocol support
* Apache 2.0 license

=== Consequences
* (+) No external dependencies
* (+) Cross-platform consistency
* (+) Programmatic access to all git data
* (-) JVM-only (hence stubs on other platforms)
* (-) Large library size

== ADR-007: Fat JAR for MCP Server Deployment

=== Status
Accepted

=== Context
MCP server needs simple deployment for end users.

=== Decision
Build fat JAR with all dependencies bundled.

=== Configuration
[source,kotlin]
----
tasks.named<Jar>("jvmJar") {
    duplicatesStrategy = DuplicatesStrategy.EXCLUDE
    manifest {
        attributes["Main-Class"] = "de.jug_da.standapp.mcp.MCPServerKt"
    }
    from({
        configurations.getByName("jvmRuntimeClasspath").map { file ->
            if (file.isDirectory) file else zipTree(file)
        }
    })
}
----

=== Consequences
* (+) Single file deployment
* (+) No classpath management
* (-) Larger file size (~50MB+)
* (-) Duplicate class handling required

== ADR-009: OpenAI-Compatible Cloud API Module

=== Status
Accepted

=== Context
The existing LLM integration options (SKaiNET kllama, JLama, REST API client) are tightly coupled to the application's internal `LLMService` interface. External tools and standard OpenAI-compatible clients cannot interact with the system directly.

=== Decision
Add a separate `cloud-api` module group providing an OpenAI-compatible REST API server, client, model DTOs, and Koog agent integration. The modules are:

* **`cloud-api:model`** - Shared `ChatCompletionRequest`/`ChatCompletionResponse` DTOs with Kotlin Serialization
* **`cloud-api:server`** - Ktor CIO server exposing `/v1/chat/completions` and `/v1/models`
* **`cloud-api:client`** - `LlmClient` HTTP client for calling the API
* **`cloud-api:agent`** - Koog `AIAgent` that starts the local server and runs agent interactions

The API contract is documented in `cloud-api/openapi.yaml` (OpenAPI 3.1).

=== Rationale
* OpenAI API is the de facto standard for LLM interaction
* Enables any OpenAI-compatible tool to use local inference
* Koog agent framework provides structured agent workflows
* Separate module group keeps cloud-api concerns isolated from core modules

=== Consequences
* (+) Standard API compatible with a wide ecosystem of tools
* (+) Clean separation from core modules
* (+) Can be deployed independently as a standalone server
* (+) Koog agent integration for advanced agent workflows
* (-) Currently uses a stub backend (echoes user messages)
* (-) Additional dependencies (Ktor server, Koog agents)

== ADR-008: Environment Variables for Configuration

=== Status
Accepted (supersedes previous system-properties-only approach)

=== Context
Need runtime configuration for LLM engine selection, model paths, and REST API endpoints. Environment variables work better with Docker, CI/CD, and MCP server stdio transport.

=== Decision
Use environment variables as the primary configuration mechanism via `LLMServiceFactory`. System properties remain supported for `getLLMSummarizer()`.

=== Environment Variables
[source,bash]
----
MCP_LLM_BACKEND=SKAINET          # or REST_API, JLAMA
MCP_LLM_MODEL_PATH=/path/to/model.gguf
MCP_LLM_REST_BASE_URL=http://localhost:11434
MCP_LLM_REST_MODEL=llama3.2:3b
MCP_LLM_REST_API_KEY=optional-key
----

=== Consequences
* (+) Zero dependencies
* (+) Works well with Docker and container orchestration
* (+) Easy to configure in Claude Desktop MCP config
* (+) `LLMBackendType.fromEnv()` provides validation at startup
* (-) Two configuration paths coexist (env vars and system properties)

== ADR-010: Adopt skainet-transformers Agent Loop with Embedded Model

=== Status
Accepted (2026-04-30)

=== Context
The previous LLM path called `KLlamaSession.generate(prompt, config)` once with a fully pre-built prompt that the CLI assembled by pulling commits with JGit and stuffing them into a `PromptBuilder`. Three things made this brittle:

* The CLI had to know the LLM's expected prompt format.
* The model had no way to ask for additional data — the operator had to pre-decide author / date window / depth.
* Distribution required users to download a multi-GB GGUF and set `MCP_LLM_MODEL_PATH` themselves.

Maven Central now has skainet 0.21.0 plus a sibling library, skainet-transformers 0.21.1, that exposes `JavaAgentLoop`, `JavaTool`, and `JavaTools.definition()` — a tool-calling agent loop layered on the existing kllama runtime.

=== Decision

. **Upgrade** to skainet 0.21.0 and adopt skainet-transformers 0.21.1, BOM-managed (per the `skainet-consumer-setup` skill: BOM at `sk.ainet`, libraries at `sk.ainet.core` / `sk.ainet.llm`).
. **Replace** the single-shot SKAINET path with `JavaAgentLoop`. The CLI hands the model a high-level task; the model calls `get_current_date`, `get_commits_by_author`, or `get_all_commits` itself.
. **Embed** Llama 3.2 1B Instruct (Q8_0, ~1.3 GB) as a JAR resource so the CLI shadow JAR (~2.0 GB) ships self-contained.
. **Default** `MCP_LLM_BACKEND` to `SKAINET` — no env vars required for the common path.
. **Keep** the REST_API backend on the legacy single-shot path with `PromptBuilder`. Remote tool calling can be added later if a user needs it.

=== Consequences

* (+) The model can answer follow-up questions ("What did Alice do last week?") without a CLI redesign — just a different task prompt.
* (+) Self-contained distribution: download the JAR, run it. No `MCP_LLM_MODEL_PATH`, no manual GGUF wrangling.
* (+) BOM-managed deps eliminate version drift across `sk.ainet.core:*` artefacts.
* (+) Single tool-calling code path; tools can be reused by future MCP / web surfaces.
* (-) Fat JAR is large (~2.0 GB). See §11 risks.
* (-) First run extracts the GGUF to `~/.cache/standapp/models/` (5-15 s). Idempotent on later runs.
* (-) Locks us to skainet-transformers' Llama 3 chat-template; switching to a non-Llama family means re-validating the agent loop.
* (-) JDK 21+ with Panama Vector remains required — same constraint as before.

=== Related

* `SKaiNET-transformers/llm-apps/kllama-java-sample/.../Main.java` — canonical Java sample used as the implementation reference.
* `skainet-consumer-setup` skill — BOM-management rules followed by `gradle/libs.versions.toml`.
