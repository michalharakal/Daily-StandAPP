== ADR-001: Privacy-First Architecture (Foundational)

=== Status
Accepted (Non-negotiable)

=== Context
Git commits contain highly sensitive information:

* Code changes revealing proprietary algorithms
* Commit messages referencing security issues, customer names, internal projects
* Author information (PII)
* Project structure and business logic

Many developers and enterprises cannot send this data to cloud services.

=== Decision
**All AI processing must run locally. No data leaves the machine.**

This is the foundational architectural constraint that drives all other decisions.

=== Consequences
* (+) Complete privacy - zero external data transmission
* (+) Compliant with enterprise security policies
* (+) Works offline
* (+) No vendor lock-in or API costs
* (-) Requires local compute resources
* (-) Model download needed for first use

== ADR-003: Pluggable LLM Architecture with SKaiNET

=== Status
Accepted

=== Context
Need local LLM inference without cloud dependencies. Options considered:
* llama.cpp (C++ with JNI bindings)
* JVM-native engines (SKaiNET, Deliverance, qxotic)
* OpenAI-compatible local servers (Ollama, LM Studio, vLLM)

=== Decision
Define `LLMService` interface for pluggable LLM backends. Use `LLMServiceFactory` to instantiate the production backends based on the `MCP_LLM_BACKEND` environment variable. Alternative JVM engines used only for benchmarking plug into the same interface from `:benchmark` so they don't pollute the production classpath.

=== Production Implementations
* **SKaiNET** (`LlamaChatLLMService` over `LlamaGenerateStage`) - Pure Kotlin model definitions, GGUF loading through SKaiNET-transformers, SIMD via Vector API plus native FFM kernels. The standup CLI drives the same stage inside the two-model pipeline of ADR-012.
* **REST API** (`RestApiLLMService`) - OpenAI-compatible HTTP endpoints (Ollama, llama.cpp server, LM Studio, vLLM, OpenAI cloud)

=== Benchmark-Only Alternative Engines
* **Deliverance** — pure-Java JVM engine; wired into `:benchmark` to demonstrate engine-independence of the `LLMService` abstraction.
* **qxotic** — alternative JVM engine; same purpose, different code path.

=== Rationale
* Pluggable architecture enables comparing multiple backends
* SKaiNET: Pure Kotlin, no native dependencies, SIMD acceleration via Java Vector API
* REST API: Leverage existing local inference servers
* Deliverance / qxotic: prove the abstraction holds across genuinely different in-process JVM engines, without forcing alternative-engine deps into the production fat JAR

=== Consequences
* (+) Two production backends available; multiple in-benchmark alternatives prove the seam
* (+) Benchmark module can compare backends side-by-side without changing the production build
* (+) No manual native library management: the FFM kernel library ships inside the `skainet-backend-native-cpu` artefact and is extracted at runtime (Panama Vector kernels remain the fallback)
* (-) Requires the JDK 25 toolchain (preview Vector API, native access) for SKaiNET
* (-) Benchmark-only engines may lag releases on Maven Central; need nested-git + `mavenLocal()` install for them

The interesting part of the architecture is not "we have an interface" — it's that the same `LLMService.generate(...)` call drives four engines that integrate the JVM in genuinely different ways (Kotlin in-process, HTTP, Java in-process, fork+exec subprocess), each pulling a model from a different source. The seam holds across all of them; that is the engine-independence claim:

----

What the diagram tells you at a glance:

* Solid boxes are production paths; dashed boxes are gated by Gradle properties at build time and never appear on the production classpath.
* Dotted arrows indicate "leaves the JVM" — the REST path crosses the network, the qxotic path crosses a process boundary. The two solid in-process engines (SKAINET, Deliverance) stay inside the same JVM as the caller.
* Each engine's *model source* is distinct — a GGUF pulled through SKaiNET's `hf://` resolver into the local cache, an OpenAI-shape HTTP server, a HuggingFace download by the engine itself, or a path supplied by the operator. The seam doesn't care; only `generate(prompt, ...)` matters.

== ADR-004: MCP Protocol for AI Assistant Integration

=== Status
Accepted

=== Context
Need to integrate with AI assistants like Claude for intelligent standup preparation.

=== Decision
Implement Model Context Protocol (MCP) server using the official Kotlin SDK.

=== Rationale
* Standard protocol supported by Anthropic
* Structured tool definitions
* JSON-RPC over stdio is simple and secure
* No network exposure required

=== Consequences
* (+) Direct integration with Claude Desktop
* (+) Standardized tool schema definitions
* (+) Secure - no network ports opened
* (-) Limited to stdio transport currently
* (-) Requires Claude Desktop configuration

== ADR-007: Fat JAR for MCP Server Deployment

=== Status
Accepted

=== Context
MCP server needs simple deployment for end users.

=== Decision
Build fat JAR with all dependencies bundled.

=== Configuration
[source,kotlin]
----
tasks.named<Jar>("jvmJar") {
    duplicatesStrategy = DuplicatesStrategy.EXCLUDE
    manifest {
        attributes["Main-Class"] = "de.jug_da.standapp.mcp.MCPServerKt"
    }
    from({
        configurations.getByName("jvmRuntimeClasspath").map { file ->
            if (file.isDirectory) file else zipTree(file)
        }
    })

=== Consequences
* (+) Single file deployment
* (+) No classpath management
* (-) Larger file size (~50MB+)
* (-) Duplicate class handling required

== ADR-009: OpenAI-Compatible Cloud API Module

=== Status
Accepted

=== Context
The existing LLM integration options (SKaiNET, REST API client) are tightly coupled to the application's internal `LLMService` interface. External tools and standard OpenAI-compatible clients cannot interact with the system directly.

=== Decision
Add a separate `cloud-api` module group providing an OpenAI-compatible REST API server, client, model DTOs, and Koog agent integration. The modules are:

* **`cloud-api:model`** - Shared `ChatCompletionRequest`/`ChatCompletionResponse` DTOs with Kotlin Serialization
* **`cloud-api:server`** - Ktor CIO server exposing `/v1/chat/completions` and `/v1/models`
* **`cloud-api:client`** - `LlmClient` HTTP client for calling the API
* **`cloud-api:agent`** - Koog `AIAgent` that starts the local server and runs agent interactions

The API contract is documented in `cloud-api/openapi.yaml` (OpenAPI 3.1).

=== Rationale
* OpenAI API is the de facto standard for LLM interaction
* Enables any OpenAI-compatible tool to use local inference
* Koog agent framework provides structured agent workflows
* Separate module group keeps cloud-api concerns isolated from core modules

=== Consequences
* (+) Standard API compatible with a wide ecosystem of tools
* (+) Clean separation from core modules
* (+) Can be deployed independently as a standalone server
* (+) Koog agent integration for advanced agent workflows
* (-) Currently uses a stub backend (echoes user messages)
* (-) Additional dependencies (Ktor server, Koog agents)

== ADR-008: Environment Variables for Configuration

=== Status
Accepted (supersedes previous system-properties-only approach)

=== Context
Need runtime configuration for LLM engine selection, model paths, and REST API endpoints. Environment variables work better with Docker, CI/CD, and MCP server stdio transport.

=== Decision
Use environment variables as the primary configuration mechanism via `LLMServiceFactory`. System properties remain supported for `getLLMSummarizer()`.

=== Environment Variables
[source,bash]
----
MCP_LLM_BACKEND=SKAINET          # or REST_API
STANDAPP_QWEN_MODEL_PATH=/path/to/Qwen3-0.6B-Q8_0.gguf            # optional, else hf:// download
STANDAPP_LLAMA_MODEL_PATH=/path/to/Llama-3.2-3B-Instruct-Q4_K_M.gguf  # optional (MCP_LLM_MODEL_PATH = legacy alias)
STANDAPP_MODEL_CACHE_DIR=~/.cache/standapp/models
STANDAPP_OFFLINE=1               # optional: never download
HF_TOKEN=optional-token
MCP_LLM_REST_BASE_URL=http://localhost:11434
MCP_LLM_REST_MODEL=llama3.2:3b
MCP_LLM_REST_API_KEY=optional-key
----

=== Consequences
* (+) Zero dependencies
* (+) Works well with Docker and container orchestration
* (+) Easy to configure in Claude Desktop MCP config
* (+) `LLMBackendType.fromEnv()` provides validation at startup
* (-) Two configuration paths coexist (env vars and system properties)

== ADR-010: Adopt SKaiNET-transformers Agent Loop with Embedded Model

=== Status
Superseded by <<adr-012,ADR-012>> (2026-09). Originally accepted 2026-04-30; kept as a historical record — the embedded 1B model, `JavaAgentLoop` and `EmbeddedModelLoader` are gone.

=== Context
The previous LLM path called `KLlamaSession.generate(prompt, config)` once with a fully pre-built prompt that the CLI assembled by pulling commits with JGit and stuffing them into a `PromptBuilder`. Three things made this brittle:

* The CLI had to know the LLM's expected prompt format.
* The model had no way to ask for additional data — the operator had to pre-decide author / date window / depth.
* Distribution required users to download a multi-GB GGUF and set `MCP_LLM_MODEL_PATH` themselves.

Maven Central now has SKaiNET 0.21.0 plus a sibling library, SKaiNET-transformers 0.21.1, that exposes `JavaAgentLoop`, `JavaTool`, and `JavaTools.definition()` — a tool-calling agent loop layered on the existing kllama runtime.

=== Decision

. **Upgrade** to SKaiNET 0.21.0 and adopt SKaiNET-transformers 0.21.1, BOM-managed (per the `skainet-consumer-setup` skill: BOM at `sk.ainet`, libraries at `sk.ainet.core` / `sk.ainet.llm`).
. **Add** a `JavaAgentLoop`-based path *alongside* the single-shot SKAINET path
(see ADR-011 for the opt-in coexistence). When opted in, the CLI hands the
model a high-level task and the model calls `get_recent_commits` itself.
. **Embed** Llama 3.2 1B Instruct (Q8_0, ~1.3 GB) as a JAR resource so the CLI shadow JAR (~2.0 GB) ships self-contained.
. **Default** `MCP_LLM_BACKEND` to `SKAINET` — no env vars required for the common path.
. **Keep** the REST_API backend on the legacy single-shot path with `PromptBuilder`. Remote tool calling can be added later if a user needs it.

=== Consequences

* (+) The model can answer follow-up questions ("What did Alice do last week?") without a CLI redesign — just a different task prompt.
* (+) Self-contained distribution: download the JAR, run it. No `MCP_LLM_MODEL_PATH`, no manual GGUF wrangling.
* (+) BOM-managed deps eliminate version drift across `sk.ainet.core:*` artefacts.
* (+) Single tool-calling code path; tools can be reused by future MCP / web surfaces.
* (-) Fat JAR is large (~2.0 GB). See §11 risks.
* (-) First run extracts the GGUF to `~/.cache/standapp/models/` (5-15 s). Idempotent on later runs.
* (-) Locks us to SKaiNET-transformers' Llama 3 chat-template; switching to a non-Llama family means re-validating the agent loop.
* (-) JDK 21+ with Panama Vector remains required — same constraint as before.

=== Related

* `SKaiNET-transformers/llm-apps/kllama-java-sample/.../Main.java` — canonical Java sample used as the implementation reference.
* `skainet-consumer-setup` skill — BOM-management rules followed by `gradle/libs.versions.toml`.

== ADR-011: Tool Calling as Opt-In Second SKAINET Path

=== Status
Superseded by <<adr-012,ADR-012>> (2026-09). Originally accepted 2026-05-05; kept as a historical record — `ToolCallingLLMService`, `SKaiNetLLMService` and `STANDAPP_TOOL_CALLING` no longer exist, and tool calling is the default path.

=== Context

ADR-010's plan to *replace* the single-shot SKAINET path with `JavaAgentLoop`
was rolled back on 2026-04-30: Llama 3.2 1B Q8_0 could not reliably emit the
tool-call JSON the loop expects, and long summarisation prompts (60+ commits)
hung for minutes inside the loop's per-round re-rendering. The default SKAINET
runtime went back to a single `KLlamaSession.generate(...)` call with a
hand-built Llama 3 turn-tag prompt.

That rollback erased the visible tool-calling surface but kept all the wiring
(SKaiNET-transformers in `build.gradle.kts`, `JavaAgentLoop` accessible at
runtime). Two things now make adding it back useful:

* The `mcp-server` module already exposes git tools to *external* clients;
  not exercising the same shape internally means we don't validate the loop
  on real workloads.
* Some prompts are short enough that a single `get_recent_commits` round
  works fine on the 1B, even if the full multi-round flow is unreliable.

=== Decision

Add `ToolCallingLLMService` as a second `LLMService` implementation, gated by
an opt-in env var. Keep `SKaiNetLLMService` (raw single-shot) as the default.

. **Two services, one interface.** Both implement `LLMService.generate(...)`.
  `LLMServiceFactory.create()` returns the default; new
  `LLMServiceFactory.createToolCallingForGit(repoDir)` returns the opt-in one.
  Selection happens in `StandAPP-cli/Main.kt` based on `STANDAPP_TOOL_CALLING=1`.
. **Single tool registered:** `get_recent_commits` (`days`, optional `author`).
  The `repoDir` is captured at construction time, never asked of the model.
. **Source-level dependency.** `settings.gradle.kts` already includes
  `../SKaiNET-transformers` as a composite build, so `ToolCallingLLMService`
  compiles against whatever version is checked out locally when that directory
  exists. The Maven coordinates pin in `gradle/libs.versions.toml` (0.36.0 as
  of 2026-07) applies whenever the composite checkout is absent.
. **Stage logging on both paths.** Every prompt-life-cycle transition emits
  a `[STAGE/...]` line on stderr — see §8.7 for the table. Without this it
  is hopeless to debug what the model is doing.
. **REST_API stays single-shot.** Remote tool calling can be added later by
  registering tools through the OpenAI-compatible API; out of scope here.

=== Consequences

* (+) Tool calling is exercisable and observable without breaking the proven
  default path. Users who want it set one env var.
* (+) The same `Tool` registry shape (`get_recent_commits`) is the model the
  MCP server exposes — schema/behaviour can converge over time.
* (+) `[STAGE/...]` logs on both paths give a uniform debugging surface.
  Rendered chat template is logged for round 0 of the agent loop, which is
  the single most useful artefact when the model misbehaves.
* (-) Two `LLMService` implementations to maintain. The shared bits
  (`formatLlama3Turn` in the raw path vs. `template.apply` in the loop) drift
  if upstream changes the chat-template format.
* (-) `JavaAgentLoop` only exposes a streaming-token callback in its public
  API. We cannot emit structured `onToolCalls` / `onToolResult` events from
  this layer — see TR-09. Mid-stream tool-call JSON is still visible in the
  streamed tokens, just not split into its own log line.
* (-) The 1B reliability problem is *not* fixed by this ADR. Long prompts
  through the loop will still hang; that is why this is opt-in, not default.

=== Related

* `llm/src/jvmMain/kotlin/de/jug_da/standapp/llm/ToolCallingLLMService.kt` — implementation.
* `llm/src/jvmMain/kotlin/de/jug_da/standapp/llm/GitTools.kt` — `GetRecentCommitsTool`.
* §6.2 (runtime view, opt-in) and §8.7 (chat templates + tool-call processing).
* TR-09 in §11 — `AgentListener` not exposed via the public `JavaAgentLoop` facade.

== ADR-012: Two-Model Pipeline on SKaiNET 0.53 — Qwen3-0.6B Tool Stage + Llama-3.2-3B Summary Stage

=== Status
Accepted (2026-09). Supersedes ADR-010 and ADR-011.

=== Context

Both earlier SKAINET designs hinged on one small model doing two jobs. The
embedded Llama 3.2 1B (ADR-010) could not reliably emit the tool-call JSON its
chat template requires, so tool calling became opt-in (ADR-011) and the
default stayed a hand-rolled single-shot prompt over the raw `KLlamaSession`.
That compromise left several things unresolved:

* The 1B summaries were mediocre and the hand-written Llama 3 turn tags drifted
  from upstream's template.
* Embedding the GGUF as a JAR resource made the CLI a ~2 GB artefact, needed a
  `uv`/Python download step at build time, and pinned the project to one model.
* The public `JavaAgentLoop` facade hid the `AgentListener` events, so tool
  calls were never observable as such (the former TR-09).
* SKaiNET had moved from 0.36 to 0.53: the decoder loader moved to
  `skainet-transformers-core`, `skainet-data-source` gained a `DataPipeline`
  DSL and an `hf://` resolver, Qwen3 got a network loader and a tool-capable
  chat template, and the kllama Java facade rejected Qwen GGUFs.

Meanwhile the app already had a pure `standapp-ai-engine` module (prompt
templates, parser, scorer) that no backend was using as a pipeline.

=== Decision

. **Upgrade** to SKaiNET core + SKaiNET-transformers 0.53.0 from Maven Central
  (BOM-managed); Kotlin 2.4.10, Ktor 3.5.2, Gradle 9.6.1, JDK 25 toolchain via
  the foojay resolver. The `../SKaiNET-transformers` composite build is opt-in
  (`-PuseLocalTransformers=true`), never implicit. Drop the kllama runtime
  dependency.
. **Split the work across two models**, each doing one job:
  * *Tool stage* — Qwen3-0.6B (Q8_0) inside `sk.ainet.apps.kllama.chat.AgentLoop`
    with `QwenChatTemplate(enableThinking = false)`, `maxToolRounds = 1`,
    192 tokens, greedy sampling, batched prefill. It calls
    `get_recent_commits(days, author?)`; `RecordingGitCommitsTool` records
    the structured commit list and the model's prose is discarded.
  * *Summary stage* — Llama-3.2-3B-Instruct (Q4_K_M) through
    `Llama3ChatTemplate` and `generateUntilStop` with the Llama 3 stop set,
    CLI temperature (default 0.1, no clamp) and top-p 0.9 paired with top-k 40.
. **Express the flow as a SKaiNET `DataPipeline`** through the app DSL
  `standupFlow { commits = qwenToolCall(); preprocess {}; prompt {};
  summarize(llama()); postprocess {}; transform(name) {}; finish(name) {} }`.
  Every step is a `PipelineStage`; `RetryingSummarizeStage` owns the
  prompt → generate → parse retry loop and reuses `PromptBuilder`,
  `SummaryParser` and `QualityScorer` from `standapp-ai-engine`.
. **Always deliver a summary.** If Qwen produces no valid call the stage logs
  `[STAGE/FALLBACK]` and fetches the commits directly (`DIRECT_FALLBACK`).
  Explicit `--since/--until` windows, `--commits git` and the `REST_API`
  backend use `GitCommitsStage` from the start.
. **Download instead of embed.** Both GGUFs are resolved on first run through
  `JvmDataSourceResolver` (`hf://` URIs) into `STANDAPP_MODEL_CACHE_DIR`
  (default `~/.cache/standapp/models`), ~0.6 GB + ~2.0 GB. Overrides:
  `--qwen-model` / `--llama-model`, `STANDAPP_QWEN_MODEL_PATH` /
  `STANDAPP_LLAMA_MODEL_PATH`, legacy `MCP_LLM_MODEL_PATH` (Llama only),
  `STANDAPP_OFFLINE=1`, `HF_TOKEN`. The shadow JAR shrinks to ~20 MB.
. **Load through the transformers DSL path**: `DecoderGgufWeightLoader.loadToMapStreaming`
  (packed, memory-mapped weights) → `QwenNetworkLoader` / `LlamaNetworkLoader.fromWeights`
  → `OptimizedLLMRuntime(DIRECT)`, with `KernelPacks.install()` +
  `FfmRowMajorKernelPack.install()` once per process. `ModelProvider.releasing()`
  loads/uses/closes each model in turn; `caching()` (`--keep-models`) keeps
  them resident.
. **Remove, don't keep alongside**: the embedded 1B JAR resource,
  `EmbeddedModelLoader`, `prepareModel` / `scripts/download-model.py`,
  `SKaiNetLLMService`, `ToolCallingLLMService`, `createToolCallingForGit`,
  `--tool-calling` / `STANDAPP_TOOL_CALLING`. `LlamaChatLLMService` implements
  `LLMService` over the Llama stage so `:benchmark`, `LLMSummarizer` and the
  `STANDAPP_TINY_PROMPT` smoke path keep working; `REST_API`, `:mcp-server`
  and `cloud-api/*` keep compiling unchanged.
. **JVM args**: `--enable-preview --add-modules jdk.incubator.vector
  --enable-native-access=ALL-UNNAMED -Xmx12g`; KV caches capped at a
  4096-token window. CI and Docker use JDK 25; the container sets
  `java.io.tmpdir=/app/tmp` on an exec-capable tmpfs and mounts the model
  cache writable.

=== Consequences

* (+) The model — not the CLI — turns the request into the git query, and the
  tool guarantees a structured result; Qwen's prose never reaches the summary.
* (+) Noticeably better summaries from the 3B model; the retry/score loop is
  shared with every other backend through the engine module.
* (+) The pipeline is extendable from Kotlin: extra tools
  (`qwenToolCall(tools = …)`), custom `transform` / `finish` stages, or an
  alternative generator (`summarize(llmService(...))`) without touching the
  built-ins. `describe()` prints the chain.
* (+) Structured `AgentListener` events (`onToolCalls`, `onToolResult`,
  `onToolCallValidationFailed`) are logged — the former TR-09 (`AgentListener` hidden behind the Java facade) is closed.
* (+) ~20 MB JAR, no build-time download step, no Python/`uv` dependency;
  published Maven artefacts instead of a mandatory sibling checkout.
* (-) First run downloads ~2.7 GB; a cold cache with `STANDAPP_OFFLINE=1` or
  without network fails with exit code 4. Privacy is unchanged: no commit data
  ever leaves the machine.
* (-) Two model loads per run. `releasing()` keeps peak memory at one model
  but reloads the summariser on every parse retry; `--keep-models` trades
  memory for speed.
* (-) CPU-only performance: on an i7-9750H the 3B summariser decodes at
  ~0.3 s/token and prefill costs about the same per token (the row-major
  kernel processes batched prefill row by row); the Qwen round adds ~40 s.
* (-) The native kernel library must be extractable to an exec-capable temp
  directory; otherwise the runtime silently falls back to slower kernels.
* (-) A 0.6B model may still skip the tool or emit an invalid call — the
  fallback hides this from the user, so `[STAGE/FALLBACK]` needs watching.
* (-) Upstream sampler quirk: `sampleFromLogits(topK = 0, topP < 1)` is
  quadratic in the vocabulary; the stage always pairs top-p with top-k 40.
