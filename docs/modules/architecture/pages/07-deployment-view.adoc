== 7.1 Infrastructure Overview

The CLI ships as a ~20 MB shadow JAR that contains all code but *no model*.
The two GGUF files — `Qwen3-0.6B-Q8_0.gguf` (~0.6 GB) and
`Llama-3.2-3B-Instruct-Q4_K_M.gguf` (~2.0 GB) — are resolved on first run
through SKaiNET's `hf://` data-source resolver into a local model cache
(`STANDAPP_MODEL_CACHE_DIR`, default `~/.cache/standapp/models`) and reused
afterwards. After that download no network access is needed
(xref:06-runtime-view.adoc[§6.3]).

The shadow JAR merges service files and additionally re-merges the two
`META-INF/services/sk.ainet.backend.api.kernel.*` entries
(`KernelProvider`, `ViewKernelPack`) — the same workaround `skainet-cli`
applies — so the native kernel provider stays discoverable.

=== Running the CLI JAR

[source,bash]
----
java --enable-preview --add-modules jdk.incubator.vector --enable-native-access=ALL-UNNAMED -Xmx12g \
  -jar StandAPP-cli/build/libs/standapp-1.0-SNAPSHOT-all.jar --repo /path/to/repo --days 7 --score
----

`./gradlew :StandAPP-cli:run` applies the same flags through
`applicationDefaultJvmArgs` (`-Xms1g -Xmx12g`). The heap holds mostly KV caches
(capped at a 4096-token window) and FP32 activations; the GGUF weights stay
packed and memory-mapped. By default the models are loaded one after the other
(`ModelProvider.releasing()`), so peak memory is one model; `--keep-models`
keeps both resident.

== 7.3 MCP Server Deployment

=== Claude Desktop Configuration

Add to Claude Desktop's MCP configuration (`claude_desktop_config.json`):

[source,json]
----
{
  "mcpServers": {
    "standapp-git": {
      "command": "java",
      "args": [
        "--enable-preview",
        "--add-modules", "jdk.incubator.vector",
        "--enable-native-access=ALL-UNNAMED",
        "-jar",
        "/path/to/mcp-server-jvm.jar"
      ],
      "env": {
        "STANDAPP_MODEL_CACHE_DIR": "/path/to/model-cache"
      }
    }
  }
}
----

`--enable-native-access` and an exec-capable `java.io.tmpdir` are required for
the native FFM kernels (`skainet-backend-native-cpu`): the bundled
`libskainet_kernels.so` is extracted to the temp directory and `dlopen`ed.
Without it the runtime *silently* falls back to the slower Panama/Vector-API
kernels (see xref:11-risks-technical-debt.adoc[§11]).

== 7.4 Docker Deployment

A `Dockerfile` and `docker-compose.yml` are provided for containerized deployment.

[source,bash]
----
# Build and run with Docker Compose
docker compose build
docker compose up
----

The image is a multi-stage build on `eclipse-temurin:25` and packages the MCP
server fat JAR. Container specifics for the local models:

* `JAVA_OPTS` carries `--enable-preview --add-modules jdk.incubator.vector --enable-native-access=ALL-UNNAMED -Djava.io.tmpdir=/app/tmp`.
* `/app/tmp` is an exec-capable tmpfs (`/tmp` itself stays `noexec`) so the native kernel library can load.
* `STANDAPP_MODEL_CACHE_DIR=/app/models`; `/app/models` is a writable volume (`./models:/app/models` in compose) that receives the first-run download and persists it across container restarts. Pre-provisioned files can be pointed at with `STANDAPP_QWEN_MODEL_PATH` / `STANDAPP_LLAMA_MODEL_PATH`.

== 7.5 Environment Variable Configuration

End users need no environment variables — `SKAINET` is the default backend
and both models are downloaded into the cache on first use. Variables exist
as overrides; CLI flags win over them.

[cols="1,2,2"]
|===
|Variable |Default |Description

|`MCP_LLM_BACKEND`
|`SKAINET`
|Backend selection: `SKAINET` (local two-model pipeline) or `REST_API`. CLI: `--backend skainet\|rest_api`.

|`STANDAPP_QWEN_MODEL_PATH`
|_(unset → download `hf://Qwen/Qwen3-0.6B-GGUF@main/Qwen3-0.6B-Q8_0.gguf`)_
|Local GGUF (or `hf://` / `https://` URI) for the tool-calling stage. CLI: `--qwen-model`.

|`STANDAPP_LLAMA_MODEL_PATH`
|_(unset → download `hf://bartowski/Llama-3.2-3B-Instruct-GGUF@main/Llama-3.2-3B-Instruct-Q4_K_M.gguf`)_
|Local GGUF (or URI) for the summariser. CLI: `--llama-model` (alias `-m` / `--model`).

|`MCP_LLM_MODEL_PATH`
|_(unset)_
|Legacy alias for `STANDAPP_LLAMA_MODEL_PATH` (summariser only); keeps existing Docker/benchmark setups that point it at "the GGUF" working.

|`STANDAPP_MODEL_CACHE_DIR`
|`~/.cache/standapp/models`
|Download cache for the `hf://` resolver.

|`STANDAPP_OFFLINE`
|_(unset)_
|`1` → never touch the network; fail fast (exit code 4) when the cache is cold.

|`HF_TOKEN`
|_(optional)_
|Hugging Face token passed by the resolver on download.

|`STANDAPP_TINY_PROMPT`
|_(unset)_
|`1` → skip the pipeline and send a one-line prompt to the summariser (download + inference smoke test).

|`MCP_LLM_REST_BASE_URL`
|`http://localhost:11434`
|Base URL for REST API backend

|`MCP_LLM_REST_MODEL`
|`llama3.2:3b`
|Model name for REST API backend

|`MCP_LLM_REST_API_KEY`
|_(optional)_
|Bearer token for authenticated REST API endpoints (falls back to `OPENAI_API_KEY`)
|===

== 7.6 Model Cache

Nothing is downloaded at build time and nothing lives in the source tree. At
runtime `ModelResolver` resolves each `ModelSpec` in this order: CLI flag →
`STANDAPP_*_MODEL_PATH` → `MCP_LLM_MODEL_PATH` (Llama only) → `hf://` download
through `sk.ainet.data.source.JvmDataSourceResolver` (Ktor CIO client with an
unbounded request timeout, progress logged every 64 MB, size sanity check
against the catalog).

[cols="1,2,3"]
|===
|Aspect |Requirement |Notes

|Format
|GGUF, packed quantisations
|Qwen3-0.6B Q8_0 (~0.6 GB) for the tool call; Llama-3.2-3B-Instruct Q4_K_M (~2.0 GB) for the summary. Both stay packed on the native kernel path.

|Architecture
|`qwen2`/`qwen3`/`qwen35` for the tool stage, `llama`/`mistral` for the summariser
|Checked from the GGUF metadata before loading; chat templates (`QwenChatTemplate`, `Llama3ChatTemplate`) follow the family automatically.

|First run
|~2.7 GB download into `STANDAPP_MODEL_CACHE_DIR`
|Once per machine; subsequent runs are cache hits. `STANDAPP_OFFLINE=1` forbids the download.

|Load time
|Memory-mapped, streaming GGUF load
|Reported as `[MODEL LOAD] … done in <ms>`; native kernels installed once per process.

|Override
|`--qwen-model` / `--llama-model` or the `STANDAPP_*_MODEL_PATH` variables
|Swap in another GGUF of the same family (e.g. a larger Qwen for the tool call) without rebuilding the JAR.
|===

== 7.8 Resource Requirements

[cols="1,2"]
|===
|Resource |Minimum Requirement

|*JDK*
|JDK 25 toolchain (auto-provisioned by the foojay resolver; JDK 21+ suffices to run Gradle)

|*RAM*
|8 GB minimum; the CLI runs with `-Xmx12g`, 16 GB recommended when using `--keep-models`

|*Disk*
|~3 GB for the model cache (~0.6 GB Qwen + ~2.0 GB Llama)

|*CPU*
|Modern x86-64 with AVX2 (native FFM kernels + Vector API). Measured on an i7-9750H: ~0.3 s/token for the 3B summariser, ~40 s for the Qwen tool round

|*Network*
|Once, for the first-run download (or pre-provisioned GGUF files + `STANDAPP_OFFLINE=1`)

|*OS*
|Linux, macOS, Windows (JVM supported platforms; native kernel library bundled per platform)
|===
