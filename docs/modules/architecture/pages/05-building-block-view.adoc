== 5.2 Module: llm (Level 2)

The LLM module provides AI inference with a pluggable architecture. Two
backends are available, selected via `MCP_LLM_BACKEND` / `--backend`
(default: `SKAINET`). The SKAINET backend is a two-model pipeline built from
`sk.ainet.data.source.PipelineStage` implementations and assembled by the
`standupFlow { }` DSL in `de.jug_da.standapp.llm.pipeline`:

----
StandupRequest → qwen-commits → require-commits → preprocess → summarize[prompt → llama → parse xN] → PipelineResult
----

=== Key Classes — pipeline

[cols="1,3"]
|===
|Class |Description

|`standupFlow(models) { }` / `StandupFlowBuilder`
|Builds a `DataPipeline<StandupRequest, PipelineResult>`. Verbs: `commits = qwenToolCall(…)` or `gitCommits()`, `preprocess { }`, `transform(name) { }`, `prompt { }`, `summarize(llama() \| llmService(…))`, `postprocess { parseSummary(); score(); retryOnInvalid(n) }`, `finish(name) { }`, `onToken`. `describe()` on the result prints the stage chain.

|`StandupRequest` / `CommitBatch` / `PromptedBatch` / `RawOutput`
|Typed payloads between stages. `CommitBatch.source` records how the commits were obtained: `QWEN_TOOL_CALL`, `DIRECT` (explicit `--since` window, REST backend, `--commits git`) or `DIRECT_FALLBACK`.

|`QwenCommitsStage`
|`StandupRequest → CommitBatch`. Drives `sk.ainet.apps.kllama.chat.AgentLoop` on Qwen3-0.6B with `QwenChatTemplate(enableThinking = false)` and `AgentConfig(maxToolRounds = 1, maxTokensPerRound = 192, temperature = 0, prefillStrategy = Batched(64))`. Registers `RecordingGitCommitsTool` plus any `extraTools`. `validate()` rejects requests with an explicit `since` (the tool is day-based). If no usable call is produced (no call, validation failure, exception) it logs `[STAGE/FALLBACK]` and delegates to `GitCommitsStage`.

|`GitCommitsStage`
|`StandupRequest → CommitBatch` through JGit directly; used for `--since/--until`, the REST backend, `--commits git` and as the Qwen fallback. Logs `[STAGE/GIT]`.

|`RequireCommitsStage`
|Throws `NoCommitsException` (exit code 3) on an empty window; otherwise logs `[STAGE/COMMITS] n commit(s) via <source>`.

|`PreprocessStage`
|Applies the engine's `preprocess { shortIds(); firstMessageLine(); limit() }` transformations to the commit list.

|`RetryingSummarizeStage`
|Composite `CommitBatch → PipelineResult`: `PromptStage` → generation stage → `SummaryParser`, re-running generation while strict parsing fails and attempts remain (the last attempt parses leniently). Runs `QualityScorer` when scoring is enabled. Exists because a linear `DataPipeline` cannot loop.

|`PromptStage`
|Renders system + user prompts from the engine's `PromptBuilder` for the request's `PromptType` (`SUMMARY` or `JSON`).

|`LlamaGenerateStage`
|`PromptedBatch → RawOutput` on Llama-3.2-3B-Instruct. Renders through `Llama3ChatTemplate`, checks the prompt fits the 4096-token window, then `generateUntilStop` with the Llama 3 stop set, batched prefill, the CLI temperature (default 0.1), top-p 0.9 paired with top-k 40. Streams tokens to `onToken`; emits the `[STAGE/INPUT\|PREFILL\|COMPLETE\|FINAL ANSWER]` logs.

|`LLMServiceGenerateStage`
|`PromptedBatch → RawOutput` through any `LLMService` — the REST backend and test fakes.

|`RecordingGitCommitsTool`
|`sk.ainet.apps.kllama.chat.Tool` named `get_recent_commits` with schema `{days: integer (required), author?: string}`. Executes `getAllCommitsInPeriod` / `commitsByAuthorAndPeriod` from `data`, stores the result in `recorded: List<GitInfo>` and returns only a short acknowledgement (the loop never feeds it back). A repeated identical call reuses the recorded list; a git failure is kept in `failure` so the stage can surface it as a git error. The repo path is captured at construction time, never asked of the model.

|`StageLog`
|`[STAGE/...]` trace lines on stderr; stdout stays reserved for the rendered summary.
|===

=== Key Classes — models and services

[cols="1,3"]
|===
|Class |Description

|`ModelCatalog` / `ModelSpec`
|The two GGUF specs: `QWEN3_0_6B` (`hf://Qwen/Qwen3-0.6B-GGUF@main/Qwen3-0.6B-Q8_0.gguf`, env `STANDAPP_QWEN_MODEL_PATH`) and `LLAMA_3_2_3B` (`hf://bartowski/Llama-3.2-3B-Instruct-GGUF@main/Llama-3.2-3B-Instruct-Q4_K_M.gguf`, env `STANDAPP_LLAMA_MODEL_PATH`). `ModelFamily` maps accepted GGUF architectures (`qwen2/qwen3/qwen35`, `llama/mistral`) to the network loader.

|`ModelResolver`
|Turns a spec into a local path: CLI flag → spec env override → `MCP_LLM_MODEL_PATH` (Llama only, legacy) → download of the `hf://` URI through SKaiNET's `JvmDataSourceResolver` into `STANDAPP_MODEL_CACHE_DIR` (default `~/.cache/standapp/models`). Overrides may themselves be `hf://`/`https://` URIs. `STANDAPP_OFFLINE=1` uses `CachePolicy.Offline`; `HF_TOKEN` is picked up from the environment. Logs progress every 64 MB and warns on a truncated file.

|`ModelProvider`
|Hands stages a loaded `LocalModel`. `releasing()` (CLI default) loads, uses and closes a model per stage so peak memory stays at one model; `caching()` (`--keep-models`, benchmark) keeps both resident.

|`LocalModel`
|Loads a GGUF via `DecoderGgufWeightLoader.loadToMapStreaming` (packed, memory-mapped weights) → `QwenNetworkLoader` / `LlamaNetworkLoader.fromWeights` → `OptimizedLLMRuntime` in `DIRECT` mode. Exposes tokenizer, `stopTokenIds` (`<\|im_end\|>`/`<\|endoftext\|>` or `<\|eot_id\|>`/`<\|end_of_text\|>`), `primaryEosTokenId` and the 4096-token `inferenceWindow`.

|`KernelSetup`
|Once per process: `KernelPacks.install()` + `FfmRowMajorKernelPack.install()` so packed weights run on the native FFM kernels (bundled `libskainet_kernels.so`, extracted to `java.io.tmpdir`) instead of the decoding reference kernel.

|`LLMService`
|JVM interface for plain prompt-in/text-out backends: `generate(prompt, maxTokens, temperature, topP): String`. Used by `:benchmark`, `LLMSummarizer` and the `STANDAPP_TINY_PROMPT` smoke path.

|`LlamaChatLLMService`
|`LLMService` over `LlamaGenerateStage` with a caching `ModelProvider`; `create(modelPath)` overrides the catalog download for the summariser.

|`LLMServiceFactory`
|Instantiates the right `LLMService` from `MCP_LLM_BACKEND` (or programmatically with `LLMBackendType` + `LLMConfig`): `LlamaChatLLMService` for `SKAINET`, `RestApiLLMService` for `REST_API`.

|`RestApiLLMService`
|OpenAI-compatible REST endpoint client (works with Ollama, llama.cpp server, LM Studio, vLLM). Always single-shot — no tool calling.
|===

NOTE: New `LLMService` backends register in `LLMServiceFactory` and can be
used as a summariser via `summarize(llmService(service))`. New tools for the
Qwen stage implement `sk.ainet.apps.kllama.chat.Tool` and are passed via
`commits = qwenToolCall(tools = listOf(MyTool()))`; because the loop runs a
single round, a tool must record its own side effects as
`RecordingGitCommitsTool` does.

== 5.4 Module: mcp-server (Level 2)

The MCP server exposes git functionality to *external* AI assistants via the Model Context Protocol. These MCP-protocol tools are distinct from the LLM agent-loop tools described in §5.2 — both surfaces use the same JGit functions (`commitsByAuthorAndPeriod`, `getAllCommitsInPeriod`) underneath, but `mcp-server` serialises them as JSON-RPC for remote clients while the `llm` module wraps them as the `get_recent_commits` `Tool` (`RecordingGitCommitsTool`) for the local Qwen model.
