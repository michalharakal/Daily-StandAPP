== 8.2 Dependency Injection

The project uses factory functions instead of a DI framework for simplicity. Two patterns coexist:

=== Pattern 1: Environment Variable Factory (MCP Server, Benchmark)

[source,kotlin]
----
// LLMServiceFactory selects backend from environment
object LLMServiceFactory {
    fun create(): LLMService {
        val backend = LLMBackendType.fromEnv() // MCP_LLM_BACKEND
        return when (backend) {
            LLMBackendType.SKAINET -> LlamaChatLLMService.create()   // Llama-3.2-3B via ModelResolver
            LLMBackendType.REST_API -> RestApiLLMService(baseUrl, model, apiKey)
        }
    }

    // Programmatic configuration (used by benchmark)
    fun create(backendType: LLMBackendType, config: LLMConfig): LLMService
}
----

[source,kotlin]

// Conditional instantiation via system properties
actual fun getLLMSummarizer(): LLMSummarizer = when {

        MockJvmLLMSummarizer()

=== Pattern 3: Pipeline DSL (StandAPP-cli)

[source,kotlin]
----
// The CLI composes the SKAINET path as a SKaiNET DataPipeline; every stage is injectable.
val models = if (cli.keepModels) ModelProvider.caching(ModelResolver(), overrides)
             else ModelProvider.releasing(ModelResolver(), overrides)
val flow = standupFlow(models) {
    commits = if (commitsMode == CommitsMode.QWEN) qwenToolCall() else gitCommits()
    preprocess { shortIds(7); firstMessageLine(120); limit(60) }
    prompt { type = promptType }
    summarize(when (backend) {
        LLMBackendType.SKAINET -> llama()
        LLMBackendType.REST_API -> llmService(restService(), name = "rest-api")
    })
    postprocess { parseSummary(); if (cli.score) score(); if (json) retryOnInvalid(maxAttempts = 2) }
    onToken = tokenSink
}
----

=== Model Lifetime and Thread Safety

Pipeline stages are `suspend` functions; inference itself runs on
`Dispatchers.Default`. `ModelProvider` serialises model resolution and loading
with coroutine `Mutex`es, and each generation starts with `runtime.reset()` so
the KV cache never carries state between calls:

[source,kotlin]
----
class CachingModelProvider(...) : ResolvingModelProvider(...) {
    private val loadLock = Mutex()

    override suspend fun <R> withModel(spec: ModelSpec, block: suspend (LocalModel) -> R): R {
        val model = loadLock.withLock { loaded.getOrPut(spec) { LocalModel.load(spec, pathFor(spec), log) } }
        return block(model)
    }
}

// LlamaGenerateStage
model.runtime.reset()
val result = model.runtime.generateUntilStop(prompt = promptTokens, eosTokenIds = model.stopTokenIds, ...)
----

`ReleasingModelProvider` (CLI default) loads a fresh `LocalModel` per
`withModel` block and closes it afterwards, so the Qwen and Llama stages never
hold two models at once. A single `LocalModel` must not be used concurrently
from two coroutines.

== 8.7 LLM Tool Calling and Generation

The SKAINET backend is a two-model pipeline (xref:09-architecture-decisions.adoc#adr-012[ADR-012]).
Qwen3-0.6B runs inside SKaiNET-transformers' `AgentLoop` for exactly one tool
round and calls `get_recent_commits`; Llama-3.2-3B-Instruct then writes the
summary from a plain system + user prompt without any tools. The `REST_API`
backend skips the tool stage and is always single-shot.

=== Tool Surface

A single built-in tool is registered on the `AgentLoop`
(extra tools can be added with `qwenToolCall(tools = listOf(…))`):

[cols="1,3,2"]
|===
|Tool |Purpose |Underlying call

|`get_recent_commits`
|List commits in the configured repo within the last `days` days (integer,
required), optionally filtered by `author` (string). Records the structured
`List<GitInfo>` for the pipeline and returns only a short acknowledgement
(`ok: n commit(s) found in the last 7 day(s)`).
|`de.jug_da.data.git.getAllCommitsInPeriod` (or
`commitsByAuthorAndPeriod` if `author` is supplied)
|===

The tool is implemented as `de.jug_da.standapp.llm.RecordingGitCommitsTool`
(`sk.ainet.apps.kllama.chat.Tool`) and takes the `repoDir` from CLI args at
construction time — the model never sees or supplies a repo path, which keeps
the privacy boundary from §4 intact. Because the loop never feeds the tool
result back to the model, the *recorded* list — not the model's prose — is what
the summariser consumes. A repeated identical call (small models sometimes emit
the same `<tool_call>` twice) reuses the recorded result; a git exception is
kept in `failure` and re-raised by the stage as `GitAccessException`.

=== Chat Templates and Tool-Call Processing

Three pieces turn the model from a text predictor into something that can call
code: the *chat template* that renders the conversation into a token stream,
the *tool-call parser* that extracts structured calls from the model's raw
output, and the *round loop* that drives the exchange.

==== Chat-template selection

Templates are selected per model family by the stage that owns the model —
there is no CLI flag and no name-based resolver:

* `QwenChatTemplate(enableThinking = false)` for the tool stage. Qwen3's ChatML
  format (`<|im_start|>role … <|im_end|>`) lists the tool definitions inside a
  `<tools>…</tools>` block of the system turn; the model answers with
  `<tool_call>{"name": …, "arguments": {…}}</tool_call>`; tool results would go
  back as `<tool_response>` inside a user turn. `enableThinking = false`
  prefills the official empty `<think></think>` block so a 0.6B model spends
  its 192-token budget on the call rather than on reasoning.
* `Llama3ChatTemplate()` for the summariser: `<|begin_of_text|>`,
  `<|start_header_id|>{system|user|assistant}<|end_header_id|>` and
  `<|eot_id|>` delimiters, rendered with `tools = emptyList()`.

Both live in `sk.ainet.apps.kllama.chat` (SKaiNET-transformers); peer formats
(`GemmaChatTemplate`, `ChatMLTemplate`, …) exist upstream. Swapping a model for
another of the same family (via `--qwen-model` / `--llama-model`) needs no
template change; a different family means a new `ModelFamily` entry and stage.

==== What the rendered prompt actually looks like

`ChatTemplate.apply(messages, tools, addGenerationPrompt = true)` produces the
full string the tokenizer sees. `QwenCommitsStage` logs it under
`[STAGE/QWEN RENDERED PROMPT]`. The shape is:

[source]
----
<|im_start|>system
You are a git assistant. You must call the get_recent_commits tool to look up commits; never answer from memory. …

# Tools
…
<tools>
{"type": "function", "function": {"name": "get_recent_commits", "description": "List the git commits …", "parameters": {"type": "object", "properties": {"days": {…}, "author": {…}}, "required": ["days"]}}}
</tools>
… return a JSON object with function name and arguments within <tool_call></tool_call> XML tags …<|im_end|>
<|im_start|>user
Fetch the git commits from the last 7 day(s) using get_recent_commits. Pass days=7 as a number.<|im_end|>
<|im_start|>assistant
<think>

</think>

----

The exact wording of the tool instructions is upstream's; the JSON schema is
`RecordingGitCommitsTool.definition`. The parser knows the format because the
same template instance handles both rendering and parsing.

For the summariser the rendered Llama 3 prompt is system + user only; the
stage logs its two halves as `[STAGE/SYSTEM PROMPT]` / `[STAGE/USER PROMPT]`.
`<|begin_of_text|>` is a control token in the GGUF vocabulary, so the stage
encodes the rendered string without adding a second BOS.

==== Tool-call parsing and validation

When the round finishes (EOS or `maxTokensPerRound = 192`), `AgentLoop` calls
`template.parseToolCalls(rawText)` and gets `List<ToolCall(id, name,
arguments: JsonObject)>`. The loop then:

. Strips thinking blocks (none with `enableThinking = false`).
. Validates each call against the JSON schema in its `ToolDefinition`. A
  failure surfaces as `AgentListener.onToolCallValidationFailed` →
  `[STAGE/TOOL VALIDATION FAILED] get_recent_commits: <reason>`; the tool is
  not invoked.
. Executes valid calls through `ToolRegistry.execute(call)` →
  `Tool.execute(arguments)`, reporting `onToolCalls` / `onToolResult`
  (`[STAGE/TOOL CALLS]`, `[STAGE/TOOL RESULT]`).

If no call is parsed, the assistant text is the final answer
(`[STAGE/QWEN RESPONSE]`).

==== The round loop

`AgentConfig(maxToolRounds = 1, maxTokensPerRound = 192, temperature = 0.0f,
prefillStrategy = PrefillStrategy.Batched(64))`. One round means:

. `template.apply(messages, tools, addGenerationPrompt = true)` — render the
  system + user turns with the tool schema.
. `runtime.generateUntilStop(...)` — batched prefill, greedy decode until
  `<|im_end|>` or the round cap, streaming tokens to the listener
  (`[STAGE/QWEN PREFILL DONE]` on the first one).
. Parse, validate, execute. Because `maxToolRounds = 1` the loop returns after
  executing the call — there is no second render with the `<tool_response>`,
  and Qwen's prose (if any) is discarded.

`QwenCommitsStage` then reads `RecordingGitCommitsTool.recorded`. If it is
empty (no call, wrong tool, validation failure, exception, exhausted budget)
the stage logs `[STAGE/FALLBACK] …` and fetches the same window through
`GitCommitsStage`; the `CommitBatch.source` says which path produced the
commits (`QWEN_TOOL_CALL` / `DIRECT_FALLBACK` / `DIRECT`).

==== Summary generation

`LlamaGenerateStage` checks the rendered prompt fits the 4096-token inference
window (`require`, with a hint to tighten `preprocess { limit(n);
firstMessageLine(...) }`), clamps `maxTokens` to the remaining window
(`[STAGE/WARN]`), then calls `generateUntilStop` with:

* `eosTokenIds` = the Llama 3 stop set `{<|eot_id|>, <|end_of_text|>}` (plus the tokenizer's EOS),
* `temperature` from the CLI (default 0.1; there is no lower clamp),
* `topP = 0.9` paired with `topK = 40` — upstream's `sampleFromLogits(topK = 0, topP < 1)` is quadratic over the 128k vocabulary (~10 s/token measured), so top-p is never used with an unbounded k,
* `prefillStrategy = Batched(64)`, progress reported as `[STAGE/PREFILL done/total]`.

`RetryingSummarizeStage` parses the output with `SummaryParser` (strict on all
but the last attempt) and re-runs generation while parsing fails and attempts
remain (`postprocess { retryOnInvalid(n) }`; the CLI uses 2 for `--format json`).

==== Logging surface

Every stage emits `[STAGE/...]` lines on stderr (`StageLog`); stdout stays
reserved for the summary. The full vocabulary:

[cols="2,3"]
|===
|Stage tag |Meaning

|`[PIPELINE] …`
|`DataPipeline.describe()` — the stage chain, e.g. `qwen-commits -> require-commits -> preprocess -> summarize[prompt -> llama -> parse x2]`.

|`[MODEL] …`
|Model resolution: `resolving <uri> (cache=…, policy=…)`, `downloading <file>: <MB>/<total MB>` every 64 MB, `cache hit`/`downloaded -> <path>`, `using local file from <origin>`, a truncated-file warning, and `released` when a releasing provider closes a model.

|`[MODEL LOAD] …`
|Loading: `<id>: arch=… family=… path=…`, then `done in <ms> — layers=… ctx=… (window 4096) vocab=… bos=… stop=…`.

|`[STAGE/QWEN]`
|Tool stage start: tool names, `maxTokens`, `temp=0.0`, `thinking=off`.

|`[STAGE/QWEN RENDERED PROMPT]`
|Full string sent to the Qwen tokenizer (system with `<tools>`, user turn, generation prompt), between `>>>` / `<<<` markers.

|`[STAGE/QWEN PREFILL DONE]`
|Time-to-first-token of the tool round in milliseconds.

|`[STAGE/QWEN RESPONSE]`
|Assistant text of the round (the raw `<tool_call>` block, or prose when the model skipped the tool).

|`[STAGE/TOOL CALLS]`
|Parsed and validated calls: `get_recent_commits({"days":7})`.

|`[STAGE/TOOL RESULT]`
|The acknowledgement string the tool returned.

|`[STAGE/TOOL VALIDATION FAILED]`
|A parsed call did not match the tool's JSON schema; the tool was not run.

|`[STAGE/QWEN COMPLETE]`
|Wall time of the whole tool round.

|`[STAGE/FALLBACK]`
|Qwen produced no usable call; the reason (calls heard, validation failures, error, last response) and the switch to direct git access.

|`[STAGE/GIT]`
|Direct JGit fetch: repo, author filter and the resolved window.

|`[STAGE/COMMITS]`
|`n commit(s) via QWEN_TOOL_CALL \| DIRECT \| DIRECT_FALLBACK`.

|`[STAGE/PROMPT]`
|Prompt type and rendered system/user prompt sizes.

|`[STAGE/INPUT]`
|Summariser call summary: model id, prompt tokens, `maxTokens`, temperature, top-p, attempt.

|`[STAGE/SYSTEM PROMPT]` / `[STAGE/USER PROMPT]`
|Full text of the two prompt halves (`>>>` / `<<<` blocks).

|`[STAGE/PREFILL]`
|Prefill progress `done/total` (every 512 tokens and at the end).

|`[STAGE/PREFILL DONE]`
|Time-to-first-token of the summariser.

|`[STAGE/COMPLETE]`
|Tokens produced, wall time, tok/s, `stoppedByEos`.

|`[STAGE/FINAL ANSWER]`
|The raw text the summariser returned — what the parser then sees.

|`[STAGE/PARSE]`
|A strict parse attempt was rejected and generation is retried.

|`[STAGE/WARN]`
|`maxTokens` clamped to fit the inference window.

|`[GitTool] get_recent_commits(...)`
|Per-invocation arguments, `result: n commit(s) recorded`, or `repeated; reusing …`. Emitted by `RecordingGitCommitsTool` itself.

|`[LLMServiceFactory] …`
|Backend selection for the `LLMService` callers (benchmark, `LLMSummarizer`, `STANDAPP_TINY_PROMPT`).
|===

=== Privacy Implications

Tool calling does not break the privacy-first guarantee from §4. The agent
loop runs entirely in-process: Qwen emits a `<tool_call>` block, `AgentLoop`
parses it, dispatches to the local tool's `execute()`, and the recorded commit
list goes straight to the in-process summariser. No network call, no cloud
assistant, no log shipping. The only network access in the whole system is the
one-time model download (§7.6), which carries no repository data.

=== Boundary with the MCP-Protocol Tools

The `mcp-server` module exposes JGit functions as MCP tools, but for a
*different consumer* (external AI assistants like Claude Desktop) and with a
different schema (separate `get_commits_by_author` and `get_all_commits`
tools, with explicit `repoDir` and ISO date arguments). Both surfaces share
the JGit backend in the `data` module. They are kept distinct so that:

* Schemas can evolve independently — the local model gets a tighter schema
  (`get_recent_commits` with an integer day count) without breaking external
  MCP clients.
* The MCP server can run headless without loading any GGUF.
* Tool-calling logic for the local LLM is unit-testable without standing up
  an MCP transport.
