= 6. Runtime View
:toc: left
:toclevels: 3
:icons: font

[IMPORTANT]
====
**Doc status (2026-05-05):** the SKAINET backend now has two paths.
The default (§6.5) is the single-shot one: CLI pre-fetches commits and hands the
model a fully-formed prompt via `SKaiNetLLMService` — no agent loop, no tool
parsing. Setting `STANDAPP_TOOL_CALLING=1` opts into the agent-loop path (§6.2):
`ToolCallingLLMService` builds a `JavaAgentLoop` with a single `get_recent_commits`
tool and lets the model drive the fetch. The 1B reliability problem from 2026-04-30
is unsolved — opt-in is the compromise. See ADR-011.
====

== 6.1 MCP Tool Call: Get Commits by Author

This scenario shows how an AI assistant retrieves commits for a specific author.

[mermaid]
----
sequenceDiagram
    participant Client as MCP Client<br/>(Claude)
    participant Transport as StdioTransport
    participant Server as MCP Server
    participant Handler as Tool Handler
    participant Git as GitClient
    participant Repo as Git Repository

    Client->>Transport: tools/call<br/>{tool: "get_commits_by_author"}
    Transport->>Server: dispatch request
    Server->>Handler: invoke tool

    Handler->>Handler: parse arguments<br/>(repoDir, author, dates)
    Handler->>Handler: parse ISO dates to Instant

    Handler->>Git: commitsByAuthorAndPeriod()
    Git->>Repo: Git.open(repoDir)
    Git->>Repo: git.log().call()
    Repo-->>Git: RevCommit[]

    Git->>Git: filter by author & dates
    Git->>Git: map to GitInfo

    Git-->>Handler: List<GitInfo>

    Handler->>Handler: format as text
    Handler-->>Server: CallToolResult
    Server-->>Transport: JSON response
    Transport-->>Client: tool result
----

== 6.2 LLM Standup Summary via Agent Loop (SKAINET, opt-in)

Opt-in via `STANDAPP_TOOL_CALLING=1`. The CLI does not pre-fetch commits — it hands
the model a short task prompt, and the agent loop drives a single `get_recent_commits`
tool call before producing the summary. See §8 (Crosscutting Concepts) for the chat
template + tool-call processing details.

[mermaid]
----
sequenceDiagram
    participant User
    participant CLI as StandAPP-cli
    participant Factory as LLMServiceFactory
    participant EML as EmbeddedModelLoader
    participant Service as ToolCallingLLMService
    participant Agent as JavaAgentLoop
    participant Model as KLlamaSession<br/>(Llama 3.2 1B Q8_0)
    participant Tool as GetRecentCommitsTool
    participant Git as JGit (data module)

    User->>CLI: STANDAPP_TOOL_CALLING=1<br/>standapp --repo R --days 7
    CLI->>Factory: createToolCallingForGit(repoDir=R)
    Factory->>EML: extract()
    EML-->>Factory: ~/.cache/standapp/models/...gguf
    Factory->>Service: ToolCallingLLMService.create(path, [GetRecentCommitsTool(R)])
    Note over Service: log [STAGE/MODEL LOAD]

    CLI->>Service: generate("Summarise the work … call get_recent_commits …")
    Note over Service: log [STAGE/INPUT], [STAGE/SYSTEM PROMPT],<br/>[STAGE/USER PROMPT], [STAGE/RENDERED CHAT TEMPLATE]
    Service->>Agent: agent.chat(prompt, tokenConsumer)

    Agent->>Model: render llama3 chat template + tool schema
    Model-->>Agent: streamed tokens incl. <tool_call>{name:get_recent_commits, args:{days:7}}
    Agent->>Tool: execute({days:7})
    Tool->>Git: getAllCommitsInPeriod(R, start, now)
    Git-->>Tool: List<GitInfo>
    Tool-->>Agent: "count=12\n- abc1234 … - …"<br/>(log [GitTool] result)

    Agent->>Model: feed tool result, re-render, continue
    Model-->>Agent: streamed tokens (final markdown summary)
    Agent-->>Service: final text
    Note over Service: log [STAGE/COMPLETE], [STAGE/FINAL ANSWER]
    Service-->>CLI: summary
    CLI-->>User: prints summary
----

NOTE: `JavaAgentLoop` exposes only a streaming-token callback in its public API.
Mid-stream tool-call markers are visible via the tokens themselves but discrete
`onToolCalls` / `onToolResult` events are not surfaced to this layer. See TR-09.

NOTE: The `REST_API` backend always uses the legacy single-shot path: the CLI
pre-fetches commits with JGit, builds a prompt via `PromptBuilder`, and calls
`service.generate(prompt)` once.

== 6.3 SKaiNET Initialisation (Embedded Model Extraction)

Shows the cold-start path the very first time the self-contained JAR runs.

[mermaid]
----
sequenceDiagram
    participant Factory as LLMServiceFactory.create()
    participant EML as EmbeddedModelLoader
    participant CL as ClassLoader
    participant FS as ~/.cache/standapp/models/
    participant KLlama as KLlamaJava.loadGGUF
    participant Builder as JavaAgentLoop.builder

    Factory->>EML: extract()
    EML->>CL: getResource("models/Llama-3.2-1B-Instruct-Q8_0.gguf")
    CL-->>EML: jar:.../standapp-all.jar!/models/...gguf

    alt cached file exists with matching size
        EML->>FS: stat target
        FS-->>EML: size matches resource length
        EML-->>Factory: target Path (no extraction)
    else first run
        EML->>FS: copy(input, target, REPLACE_EXISTING)
        Note over EML,FS: ~1.3 GB — takes 5–15s on local disk
        EML-->>Factory: target Path
    end

    Factory->>KLlama: loadGGUF(target, systemPrompt=null)
    KLlama-->>Factory: KLlamaSession

    alt STANDAPP_TOOL_CALLING=1
        Factory->>Builder: session().tool(GetRecentCommitsTool).template("llama3").build()
        Builder-->>Factory: JavaAgentLoop
        Factory-->>Factory: ToolCallingLLMService instance
    else default
        Factory-->>Factory: SKaiNetLLMService instance<br/>(raw KLlamaSession.generate path)
    end
----

== 6.5 LLM Standup Summary — Default SKAINET Path (Single-Shot)

This is the default flow when `STANDAPP_TOOL_CALLING` is unset. The CLI fetches
commits with JGit, formats them via `PromptBuilder`, and `SKaiNetLLMService` wraps
the prompt in Llama 3 turn tags before a single `KLlamaSession.generate(...)` call.
No agent loop, no tool parsing.

[mermaid]
----
sequenceDiagram
    participant User
    participant CLI as StandAPP-cli
    participant PB as PromptBuilder
    participant Service as SKaiNetLLMService
    participant Model as KLlamaSession<br/>(Llama 3.2 1B Q8_0)
    participant Git as JGit (data module)

    User->>CLI: standapp --repo R --days 7
    CLI->>Git: getAllCommitsInPeriod(R, start, now)
    Git-->>CLI: List<GitInfo>
    CLI->>PB: buildUserPrompt(commits, SUMMARY)
    PB-->>CLI: "Given the following Git commits …\n{{commits}} → expanded"

    CLI->>Service: generate(prompt, temperature, topP)
    Note over Service: log [STAGE/SYSTEM PROMPT],<br/>[STAGE/USER PROMPT],<br/>[STAGE/WRAPPED PROMPT (Llama 3 turn tags)]
    Service->>Model: generate(wrappedPrompt, GenerationConfig)
    Model-->>Service: streamed tokens
    Note over Service: log [STAGE/PREFILL DONE] on first token,<br/>[STAGE/COMPLETE], [STAGE/FINAL ANSWER]
    Service-->>CLI: summary
    CLI-->>User: prints summary
----

    Setup->>Server: addTool("get_all_commits", ...)

    Setup->>Stdin: asInput()

    Setup->>Server: connect(transport)
    Server-->>Setup: session

    Setup->>Transport: onClose { done.complete() }

    Note over Setup: runBlocking { done.join() }
    Note over Setup: Server running...<br/>waiting for requests
----

== 6.5 Cloud API Request Flow

This scenario shows how an external client interacts with the cloud-api server via the OpenAI-compatible REST API.

[mermaid]
----
sequenceDiagram
    participant Client as HTTP Client<br/>(LlmClient / curl)
    participant Server as LocalAIServer<br/>(Ktor CIO)
    participant Handler as Route Handler
    participant Model as Response Builder

    Client->>Server: POST /v1/chat/completions<br/>{model, messages}
    Server->>Handler: dispatch request

    Handler->>Handler: parse JSON body
    Handler->>Handler: extract model & messages
    Handler->>Handler: find last user message

    Handler->>Model: build ChatCompletionResponse
    Model-->>Handler: response with choices & usage

    Handler-->>Server: respond(response)
    Server-->>Client: 200 OK<br/>{id, choices, usage}

    alt Error
        Handler-->>Server: 500 error JSON
        Server-->>Client: {"error": {...}}
    end
----

== 6.7 Error Handling Flow

[mermaid]
----
sequenceDiagram
