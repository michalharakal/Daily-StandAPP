= Inference Stages: Tokens → Prefill → Decode → (Tool) → Decode
:toc: left
:icons: font

What happens between "a pipeline stage hands the model a prompt" and
"text comes back". This page is the level *below*
xref:explanation/agent-loop-internals.adoc[Agent-loop internals] —
where that page treats the model call as a black box, this one opens
the box.

Knowing these stages lets you:

* Read benchmark numbers without confusion (TTFT vs tok/s measure
  different things).
* Diagnose stalls correctly (was it model loading, prefill or decode?).
* Design prompts that don't pay costs you didn't intend.
* Make sense of why a summary takes minutes on a laptop CPU even though
  the answer is 250 tokens long.

Both models in the pipeline go through the same stages; the tool stage
(Qwen3-0.6B) adds the tool branch, the summariser (Llama-3.2-3B) does
not.

== The full pipeline

[mermaid]
----
sequenceDiagram
    autonumber
    actor U as User
    participant A as App / Orchestrator
    participant T as Tokenizer
    participant L as LLM
    participant K as KV Cache
    participant X as External Tool/API

    U->>A: Send prompt
    Note over A: Build full context<br/>system prompt + history + user input<br/>optional docs/tools/schema

    A->>T: Tokenize context
    T-->>A: Input tokens

    A->>L: Start inference with input tokens
    Note over L: PREFILL STAGE

    L->>L: Embed tokens
    L->>L: Run transformer layers over all input tokens
    L->>K: Store key/value states for prompt tokens
    L-->>A: Next-token logits / first decision point

    Note over L,A: DECODE STAGE starts

    A->>L: Generate next token
    L->>K: Reuse cached prompt states
    L-->>A: Token or structured output

    alt Model answers directly
        loop Generate until stop
            A->>L: Generate next token
            L->>K: Reuse/update KV cache
            L-->>A: Output token
        end
        A-->>U: Final answer
    else Model decides to call a tool
        L-->>A: Tool call request (name + arguments)
        A->>X: Execute tool
        X-->>A: Tool result

        Note over A: Append tool result to conversation

        A->>T: Tokenize updated conversation
        T-->>A: Updated tokens

        A->>L: Run inference again on updated context
        Note over L: SECOND PREFILL

        L->>L: Process newly provided tool result
        L->>K: Refresh / extend KV cache
        L-->>A: Next-token logits

        loop Generate final response
            A->>L: Generate next token
            L->>K: Reuse/update KV cache
            L-->>A: Output token
        end

        A-->>U: Final answer using tool result
    end
----

The numbered stages below correspond to phases in the diagram. In this
app the tool branch stops after "Execute tool": the loop runs one round
and the tool's *recorded* result goes to the next pipeline stage, not
back into the model.

== 0. Model loading (before any of this)

Nothing in the diagram can start until a `LocalModel` exists.
`ModelProvider.withModel(spec)` resolves the GGUF (cache or first-run
download, `[MODEL]` lines) and `LocalModel.load` builds the runtime
(`[MODEL LOAD]` lines):

. `KernelSetup.ensureInstalled()` — once per process —
  `KernelPacks.install()` and `FfmRowMajorKernelPack.install()`. The
  second installs the native FFM kernels; the bundled
  `libskainet_kernels.so` is extracted to `java.io.tmpdir` and loaded
  through the Foreign Function & Memory API (hence
  `--enable-native-access=ALL-UNNAMED`). If that directory is mounted
  `noexec` the load fails *silently* and everything falls back to the
  decoding reference kernel — correct, but many times slower.
. `DecoderGgufWeightLoader.loadToMapStreaming` streams the weights and
  keeps them *packed* (Q8_0 / Q4_K / Q6_K) and memory-mapped. No
  dequantised FP32 copy lives on the heap; the row-major kernels
  consume the packed blocks directly.
. `QwenNetworkLoader.fromWeights` / `LlamaNetworkLoader.fromWeights`
  builds the network for the family; `OptimizedLLMRuntime` in
  `OptimizedLLMMode.DIRECT` executes it.
. The KV cache is sized for `min(contextLength, 4096)` tokens
  (`LocalModel.MAX_INFERENCE_LEN`).

With the default `ModelProvider.releasing()` this happens twice per run
(Qwen, then Llama) and each model is closed before the next loads;
`--keep-models` keeps both resident.

== 1. Context assembly (orchestrator)

Before the model sees anything, the pipeline stage builds the full
*context string* through the family's chat template. For the tool stage,
`QwenChatTemplate(enableThinking = false)` renders:

[source]
----
<|im_start|>system
You are a git assistant. You must call the get_recent_commits tool …

# Tools
…
<tools>
{"type":"function","function":{"name":"get_recent_commits",…}}
</tools>
…<|im_end|>
<|im_start|>user
Fetch the git commits from the last 7 day(s) using get_recent_commits. Pass days=7 as a number.<|im_end|>
<|im_start|>assistant
<think>

</think>

----

For the summariser, `Llama3ChatTemplate` renders system + user turns with
no tool schema. xref:reference/chat-templates.adoc[Reference: chat
templates] shows both in full; `[STAGE/QWEN RENDERED PROMPT]` and
`[STAGE/SYSTEM PROMPT]`/`[STAGE/USER PROMPT]` log what was actually
sent.

The string is *just text* at this point — nothing model-specific yet.

== 2. Tokenization

`Tokenizer.encode(string)` maps the context string into a sequence of
*token IDs* — integers in `[0, vocabSize)`. The tokenizer is built from
the GGUF itself (`TokenizerFactory.fromGgufSource`), so it always matches
the checkpoint. Llama 3's vocabulary has 128 256 entries, Qwen3's
151 936; both are byte-pair encoding (BPE).

Why this stage matters:

* **Tokens are the unit of cost.** Every "1.4 KB string" of commit text
  in the user prompt is really N tokens for some N — and prefill cost
  scales with N, not with the byte count. `[STAGE/PROMPT]` reports
  characters; `[STAGE/INPUT] promptTokens=…` reports the truth.
* **Tokenization is reversible.** `tokenizer.decode(id)` reproduces the
  exact byte sequence the encoder consumed. The streaming output you
  see in the CLI is `decode(tokenId)` per generated token.
* **Special tokens are real tokens.** `<|eot_id|>`, `<|im_end|>`,
  `<|begin_of_text|>` etc. each occupy one token ID. Because
  `<|begin_of_text|>` is a control token in the vocabulary, the
  summariser encodes the rendered template as-is and does not add a
  second BOS. The chat template's structural overhead is small
  (~5–10 tokens per turn) — most of your prompt is content, not wrapping.
* **The window is checked here.** If the prompt alone does not fit the
  4096-token window the stage refuses with a message telling you to use
  `preprocess { limit(n); firstMessageLine(…) }`; if prompt + budget do
  not fit, `maxTokens` is clamped (`[STAGE/WARN]`).

== 3. Prefill stage

The model takes the full input token sequence and runs it through the
transformer to fill the KV cache. `generateUntilStop` is called with
`PrefillStrategy.Batched(64)`: the prompt is fed in chunks of 64 tokens
rather than one token at a time.

What happens internally:

. **Embedding lookup.** Each token ID becomes a `dim`-wide float
  vector. For Llama 3.2 3B, `dim = 3072`; for Qwen3-0.6B, `1024`.
. **Transformer layers.** Each of the model's layers (28 for both of our
  checkpoints) runs attention + feed-forward over the chunk. Attention
  is quadratic in sequence length, feed-forward is linear.
. **KV cache fill.** For every layer's attention, the *key* and
  *value* tensors for every input token get written to the
  pre-allocated KV cache. This is what lets decode stay linear later.

Critical numbers to remember — measured on an i7-9750H (6C/12T) with the
native FFM row-major kernels:

* **Prefill costs about as much per token as decode on this kernel:
  ≈ 0.3 s per prompt token for Llama-3.2-3B Q4_K_M.** The row-major
  kernel processes a batched prefill row by row, so batching saves the
  per-call overhead but not the matmul work. A 400-token summariser
  prompt therefore waits roughly two minutes before the first token.
  This is the single biggest reason to keep the commit list short.
* The Qwen tool round — a ~300-token tool prompt plus a ~30-token
  answer on a 0.6B — takes ≈ 40 s end to end.
* Prefill is wall-clock time the user *waits* for. There is nothing to
  display until the first token of decode arrives — that's
  **time-to-first-token (TTFT)**, logged as `[STAGE/PREFILL DONE]`
  (summariser) and `[STAGE/QWEN PREFILL DONE]` (tool stage). The
  summariser additionally logs `[STAGE/PREFILL] done/total` every 512
  tokens so a long prefill is visibly alive.

== 4. Decode stage (autoregressive)

Once prefill finishes, decode generates one token at a time:

. Take the most recent token's last-layer hidden state → multiply by
  the unembedding matrix → produce *logits* (vocabulary-wide
  scores).
. Sample from logits using temperature, top-p, top-k → one new token
  ID.
. Append that ID to the input. The KV cache already has all prior
  positions, so the next forward pass only computes attention for the
  *one new position* against the cached keys/values. **This is why
  decode is linear**, not quadratic.
. Repeat until the model emits a stop token or hits `maxTokens`.

How the two stages sample:

[cols="1,2,2"]
|===
| |Tool stage (Qwen) |Summariser (Llama)

|Temperature
|`0.0` — greedy; there is exactly one right answer (the call)
|`--temperature`, default `0.1`; no clamping

|Top-p / top-k
|n/a (greedy)
|`topP = 0.9`, paired with `topK = 40`

|Stop tokens
|`<\|im_end\|>` (primary EOS for the agent loop)
|`{<\|eot_id\|>, <\|end_of_text\|>}` via `generateUntilStop(eosTokenIds = …)`

|Budget
|`maxTokensPerRound = 192`
|`--max-tokens`, default 512, clamped to the window
|===

[IMPORTANT]
====
**Why top-p is always paired with top-k.** Upstream's `sampleFromLogits`
with `topK = 0` (meaning "all") and `topP < 1` sorts the full vocabulary
with an insertion loop that is quadratic in the 128k Llama vocabulary —
about 10 s *per token* measured. `LlamaGenerateStage` therefore passes
`topK = 40` (llama.cpp's default) whenever nucleus sampling is active,
and `topK = 0` only when `topP == 1`. If you ever see decode at several
seconds per token with a healthy prefill, check the sampler settings
before blaming the kernels.
====

Two more key facts:

* **Decode is the throughput stage** — but `[STAGE/COMPLETE] … tok/s`
  divides by the *total* wall time including prefill, so on a long
  prompt the number looks worse than the per-token decode speed. On the
  i7-9750H the 3B decodes at roughly 0.3 s per token (≈ 3 tok/s).
* **The KV cache is per-generation.** Each `LlamaGenerateStage.process`
  call starts with `runtime.reset()`; a JSON retry re-prefills the whole
  prompt. The cache is allocated for the 4096-token window up front,
  which together with the memory-mapped weights is why the CLI runs with
  `-Xmx12g`.

== 5. Tool-call branch

Only the tool stage takes this branch. When Qwen's decode finishes, the
agent loop:

. **Parses** the tool call out of the raw decoded text —
  `<tool_call>{…}</tool_call>`, handled by the Hermes strategy (see
  xref:reference/tool-call-parsers.adoc[the parser reference]).
  `[STAGE/TOOL CALLS]` shows what was parsed.
. **Validates** the arguments against the tool's JSON schema
  (`[STAGE/TOOL VALIDATION FAILED]` on failure — the tool does not run).
. **Executes** the tool — `RecordingGitCommitsTool` calls JGit
  (`[GitTool]` lines) and *records* the structured commit list on the
  tool object. This is where the diagram's `X` actor is involved.
. Returns the tool's short acknowledgement string as the tool result
  (`[STAGE/TOOL RESULT]`).

In the general loop, step 4 would be followed by appending the result as
a `TOOL` message, `runtime.reset()`, and a **second prefill** over the
whole longer conversation. Here `maxToolRounds = 1`, so the loop returns
right after executing the tools and no second prefill ever happens. The
pipeline reads `tool.recorded` and moves on to `require-commits`,
`preprocess` and the summariser. If nothing usable was recorded, the
stage logs `[STAGE/FALLBACK]` and fetches the commits directly.

== 6. Second prefill (why we avoid it)

The generic agent loop re-renders and re-prefills the *entire*
conversation on every round:

* Round 0: prefill ~300 tokens.
* Round 1: prefill 300 + (tool call + tool result + headers) ≈ 600 tokens.
* Round 2: prefill 600 + (next call/result) ≈ 900 tokens.
* And so on, up to `maxToolRounds`.

At ≈ 0.3 s per prompt token this is minutes per round on the 3B, and
the value of the extra rounds on a 0.6B is low: a second round would
only let Qwen paraphrase the acknowledgement string. Handing the
structured commit list to a dedicated summariser is both faster and
better than asking the tool model to write prose from a tool response.

There's a known optimisation (*prefix-shared KV caches* — keep state
for the unchanged prefix and only prefill the new TOOL message suffix)
that neither this app nor SKaiNET-transformers' `AgentLoop` implements.
It's an upstream improvement opportunity, not a configuration we can
flip on — and with one round it is not needed.

== 7. Final decode

The summariser's decode (step 4) *is* the final decode of the pipeline:
tokens stream to stdout (Markdown without `--output`), then
`[STAGE/COMPLETE]` and `[STAGE/FINAL ANSWER]` close the generation. With
`--format json`, a strict-parse failure (`[STAGE/PARSE]`) re-runs steps
1–4 for the summariser once more.

== Performance implications

[cols="2,3"]
|===
|Observation |Why

|Prompt length matters as much as output length on this CPU path.
|Prefill and decode cost about the same per token on the row-major
kernel. A 400-in/250-out summary spends roughly half its wall time
before the first token. `preprocess { firstMessageLine(120); limit(60) }`
exists for this reason.

|Streaming output starts only after prefill finishes.
|There is no token to stream until step 4 begins. A long prefill looks
identical to a hung process — `[STAGE/PREFILL] n/total` and
`[STAGE/PREFILL DONE]` are the signals that it is alive and that decode
has started.

|The tool stage is a fixed ~40 s overhead.
|A 0.6B model on a ~300-token tool prompt. `--commits git` skips it
entirely when you only need the summary.

|A wrong sampler configuration can cost more than the model.
|`topK = 0` with `topP < 1` makes sampling quadratic in the vocabulary
(~10 s/token). Keep top-p paired with a finite top-k.

|A `noexec` temp directory makes everything slow, not broken.
|The native kernel library is extracted to `java.io.tmpdir` and loaded
from there; when that fails the reference kernel runs instead. The Docker
image sets `java.io.tmpdir=/app/tmp` on an exec-capable tmpfs for this
reason.

|KV cache size dictates max context.
|The window is `min(ctx, 4096)` tokens. Prompts beyond it are rejected,
budgets beyond it are clamped (`[STAGE/WARN]`).
|===

== Diagnosing with `[STAGE/...]` logs

Mapping the diagram to the
xref:reference/stage-logs.adoc[stage-log reference]:

[cols="1,2"]
|===
|Pipeline phase |Log lines you'll see

|0. Model loading
|`[MODEL] … resolving/cache hit/downloaded`, then the two
`[MODEL LOAD]` lines. A gap between them is disk IO plus kernel-pack
installation.

|1. Context assembly
|`[STAGE/QWEN]` + `[STAGE/QWEN RENDERED PROMPT]` (tool stage);
`[STAGE/PROMPT]`, `[STAGE/SYSTEM PROMPT]`, `[STAGE/USER PROMPT]`
(summariser).

|2. Tokenization
|`[STAGE/INPUT] promptTokens=…` (summariser). Tokenization itself is
microseconds; a long pause after it is prefill.

|3. Prefill
|`[STAGE/PREFILL] done/total` every 512 tokens, then
`[STAGE/PREFILL DONE]` / `[STAGE/QWEN PREFILL DONE]` with the TTFT.

|4. Decode
|Streaming token output to stdout (summariser). Throughput and
`stoppedByEos` in `[STAGE/COMPLETE]`; the raw tool-stage answer in
`[STAGE/QWEN RESPONSE]`.

|5. Tool execution
|`[STAGE/TOOL CALLS]`, `[GitTool] get_recent_commits(...)`,
`[GitTool] result: …`, `[STAGE/TOOL RESULT]`, or
`[STAGE/TOOL VALIDATION FAILED]`; then `[STAGE/QWEN COMPLETE]`.

|6. Second prefill
|Never happens (`maxToolRounds = 1`). `[STAGE/FALLBACK]` + `[STAGE/GIT]`
appear instead when the round produced no usable call.

|7. Final decode
|Continued streaming + final `[STAGE/COMPLETE]` and `[STAGE/FINAL ANSWER]`;
`[STAGE/PARSE]` if a JSON attempt was rejected.
|===
