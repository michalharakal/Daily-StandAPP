= Why Prompts Matter on Small Models
:toc: left
:icons: font

The pipeline runs on a 0.6B model (Qwen3, the tool call) and a 3B
model (Llama 3.2, the summary) — roughly a *thousandth* of the capacity
of GPT-4 or Claude. Tactics that feel like superstition on a frontier
model are load-bearing at this size. This page is the conceptual
argument behind
xref:how-to/tune-prompts-for-small-models.adoc[the tuning how-to].

== Capacity, structure, and the structural prior

A language model is a function that, given a prefix, outputs a
probability distribution over the next token. At every step it is
*sampling* from that distribution.

A frontier model has enough internal structure that even a vague
instruction ("summarise these commits") seeds a coherent output
distribution. The model has seen hundreds of standup-report examples in
training; it has an internal template it can imitate.

A 3B model has far less of it, and a 0.6B almost none. Its internal
"standup report" prior is much weaker. Asked to "summarise these
commits", it might:

* Repeat the input verbatim (low-entropy mode).
* Drift into pleasantries ("That's a great set of commits!").
* Generate plausible-looking but unrelated content.
* Hallucinate commit IDs and authors that aren't in the input.

The fix is to *give it a structural prior in the prompt* — explicit
section headings, slot-filling instructions, and short examples. The
model no longer has to invent the structure; it has to fill in slots.
Slot-filling is much easier than free generation for a small model.

== Why explicit headings work

This is the difference between:

[source,subs="-attributes"]
.Open-ended (high-capacity-needed)
----
Summarise these commits as a daily standup report.

{{commits}}
----

…and:

[source,subs="-attributes"]
.Skeleton (low-capacity-needed)
----
Produce a report with three sections:

## Yesterday
(work completed)

## Today
(planned work)

## Blockers
(obstacles, or "None")

Commits:
{{commits}}
----

The skeleton constrains the output distribution at every section
boundary. After "## Yesterday\n", the model's next-token distribution
sharply favours summary-prose tokens; after "## Blockers\n", it sharply
favours short bullets or "None". The model spends its capacity on
*content* rather than *format invention*.

This is why `DefaultPrompts.SUMMARY_USER` looks the way it does. The
parenthetical instructions per heading are not for stylistic flourish —
they're additional structural anchors that tell the model what kind of
content goes in each slot.

== Why "exactly once" is enforced by the loop, not the prompt

A small model can't reliably count, and "exactly once" is a counting
constraint. The tool-stage system prompt still says it:

[source]
----
… Call the tool exactly once with the days (integer) and, only if the
user names one, the author from the request.
----

…but the pipeline no longer *depends* on the model honouring it. The
retired single-model prompt asked a 1B to call the tool once *and then*
write the summary; the model routinely called it several times, not at
all, or malformed. Today:

* The loop runs one round (`maxToolRounds = 1`), so a second call can't
  happen in a later turn.
* Two identical calls in the same turn are collapsed by the tool
  (`[GitTool] … repeated`).
* Thinking is disabled through the template's empty `<think></think>`
  prefill, so the 0.6B doesn't spend its budget reasoning about the
  instruction.
* No call, or an invalid one, falls back to direct git access.

The prompt's remaining job is to make the *first* output a well-formed
call — restating `days` as a number and the argument names is what
helps a 0.6B most. The lesson generalises: put counting and sequencing
constraints in code, and leave the model a single slot to fill.

== Token-budget reasoning: why prefill cost dominates

Inference time on CPU is roughly:

[source]
----
total_time ≈ prefill_time + (generated_tokens × per_token_time)
----

For the 3B Q4_K_M summariser on an i7-9750H with the native FFM
row-major kernels:

* `per_token_time` ≈ 300 ms.
* `prefill_time` is *also* ≈ 300 ms per *input* token — the row-major
  kernel processes a batched prefill row by row, so prefill is not the
  cheap matrix multiply it is on a GPU.

So a 200-token prompt with 200 tokens of output costs:

[source]
----
200 × 0.3s + 200 × 0.3s = 60s + 60s ≈ 2 min
----

But a 2000-token prompt with the same 200-token output costs:

[source]
----
2000 × 0.3s + 200 × 0.3s = 600s + 60s ≈ 11 min
----

Every input token costs as much as an output token, and the window is
4096 tokens anyway. This is why the CLI's `preprocess { shortIds(7);
firstMessageLine(120); limit(60) }` is not cosmetic: a multi-paragraph
commit body multiplies prompt tokens without adding signal.

The tool stage adds a fixed ≈ 40 s for its ~300-token prompt on the
0.6B. Had the loop been allowed a second round, the *entire*
conversation would be re-rendered and re-prefilled — the mechanism that
produced the 14-minute prefill in
xref:explanation/negative-sample-2026-05-05.adoc[the negative sample]
on the retired single-model path. One round avoids it.

The takeaway: *keep prompts short* on small models. On the summariser
the commit list is the worst offender; on the tool stage it would be the
system prompt, because it is rendered together with the tool schema.

== When to give up on small models

For some tasks, no amount of prompt tuning rescues a 0.6B or 3B:

* Complex reasoning with chained tool calls (frontier-model territory).
* Anything that requires accurate counting or arithmetic.
* Tasks with strict JSON-output requirements *and* nontrivial content
  (the model picks one to do well).
* Tasks with subtle constraint composition ("X but only when Y unless Z").

The signal: if your prompt is more than ~500 chars and includes
multiple "but" or "unless" clauses, you've outgrown the local models.
Split the task across stages (the tool call and the summary are already
two models for this reason), or switch the summariser to a 7B+ through
the REST path (Qwen 3 7B Instruct, Llama 3.1 8B) — see
xref:reference/model-selection.adoc[].
