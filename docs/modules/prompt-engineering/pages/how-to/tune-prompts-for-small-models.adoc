= Tune Prompts for Small Models
:toc: left
:icons: font

The pipeline runs two small models: Qwen3 0.6B (Q8_0) for the tool call and
Llama 3.2 3B Instruct (Q4_K_M) for the summary. Both are small enough that
prompt *shape* matters more than instruction wording. The same task that
works on Claude or GPT-4 with a casual one-liner needs structural
scaffolding here — and the 0.6B tool model needs it even more than the 3B
summariser.

This page collects tactics that empirically work, with before/after
examples drawn from this codebase.

== Where the prompts live

[cols="1,2,2"]
|===
|Stage |Prompt source |How to override

|`qwen-commits` (0.6B)
|`QwenCommitsStage.DEFAULT_SYSTEM_PROMPT` plus a user turn generated from
the request (`Fetch the git commits from the last N day(s) … Pass days=N as
a number.`). The tool schema is rendered by `QwenChatTemplate`.
|`commits = qwenToolCall(systemPrompt = "…")` in `standupFlow`; the user
turn is fixed by the stage.

|`llama` (3B)
|`DefaultPrompts.SYSTEM`, `DefaultPrompts.SUMMARY_USER`,
`DefaultPrompts.JSON_USER` in `standapp-ai-engine`, rendered by
`PromptBuilder` through the `PromptStage`.
|`prompt { system = "…"; summaryTemplate = "…"; jsonTemplate = "…" }` in
`standupFlow` (a `PromptSpec`).
|===

== Tactic 1: provide a structural skeleton

A small model is much better at *filling in slots* than at *generating a
structure from scratch*. Tell it the exact section headings and let it
fill in the content.

[source,markdown]
.Before — open-ended (works on a 7B+, fragile on a 3B)
----
Summarise the following git commits as a daily standup report.

{{commits}}
----

[source,markdown]
.After — explicit skeleton (`DefaultPrompts.SUMMARY_USER`)
----
Given the following Git commits, produce a concise standup report with
exactly these three markdown headings:

## Yesterday
(Summarise work completed based on the commits)

## Today
(Infer planned work as a continuation, or state "Continue work on …")

## Blockers
(List any obstacles mentioned in commit messages, or "None")

Reference commit IDs where relevant. Be concise and actionable.

Commits:
{{commits}}
----

The "After" version is what's currently in
`standapp-ai-engine/.../control/PromptBuilder.kt`. The skeleton anchors the
output, so the model can spend its capacity on content rather than format
invention.

== Tactic 2: keep system prompts short

Every token in the system message is processed on every prefill. On the
row-major kernel prefill costs about as much per token as decode (~0.3 s per
token for the 3B on an i7-9750H), so 200 extra system tokens are a minute of
wall time. The summariser's system prompt (`DefaultPrompts.SYSTEM`) is one
sentence; the Qwen system prompt is three. Anything in the system that
doesn't change *the model's behaviour* is wasted prefill cost.

If you're tempted to write a long persona, instead write a *one-line*
persona and put the constraints in the user message.

== Tactic 3: name a single output format

Saying "respond with JSON or markdown" doubles the model's choice space.
Pick one. The `DefaultPrompts.JSON_USER` template makes one choice — JSON
only, with a worked schema — and `--format json` switches the whole flow to
it (`prompt { type = PromptType.JSON }`).

== Tactic 4: lead with an instruction, not context

Bad order:

[source]
----
Here are the commits: …
Now write a standup summary.
----

Better order:

[source]
----
Write a standup summary with three sections (## Yesterday, ## Today,
## Blockers). Use these commits:
…
----

The instruction at the top is in the model's working memory throughout
generation; an instruction at the bottom of a long context is more likely
to be ignored or corrupted.

== Tactic 5: avoid open-ended choices

"Decide whether the commits indicate progress or not" → bad.
"Pick one of: progress / blocked / unclear. Justify in one sentence." → good.

A small model is much better at picking from an enumeration than at
producing a free-form judgement.

== Tactic 6: one job per model

The reason the pipeline uses two models is a prompt-engineering one. Asking
a single small model to *call a tool and then summarise* mixes two tasks in
one prompt, and the retired single-model path showed what happens: the
model hallucinated a tool call inside markdown fences and then invented
commits. Now each prompt asks for exactly one thing:

* Qwen's system prompt says *call `get_recent_commits` exactly once, never
  answer from memory*; the user turn even spells out the argument
  (`Pass days=7 as a number`). Thinking is disabled so the 192-token budget
  goes to the call, and sampling is greedy (`temperature = 0`).
* Llama's prompt contains the commits already and asks only for the report.

If you change the Qwen system prompt, keep it imperative and keep the tool
name in it. Watch `[STAGE/QWEN RESPONSE]` for `<tool_call>` and
`[STAGE/FALLBACK]` for the failure reason.

== Tactic 7: sampling — low temperature is fine now

The CLI default is `--temperature 0.1`, passed through to Llama unchanged;
there is no floor. The old `>= 0.6` clamp existed because the raw-session
path collapsed into repetition at low temperatures, and the chat-template
path does not have that problem. Nucleus sampling uses `topP = 0.9` paired
with `topK = 40` (`LlamaGenerateStage.DEFAULT_TOP_K`) — the pairing is
mandatory for speed, see xref:explanation/inference-stages.adoc[inference
stages]. For determinism tests use `llama(seed = 42L)` in the DSL.

Qwen is greedy (`temperature = 0`) regardless of the CLI flag.

== Tactic 8: mind the window

Both models run with a 4096-token KV cache window. `LlamaGenerateStage`
refuses a prompt that does not fit and clamps `maxTokens` (default 512) to
the remaining budget, logging `[STAGE/WARN] maxTokens clamped …`. The CLI's
`preprocess { shortIds(7); firstMessageLine(120); limit(60) }` keeps a
typical repo well inside; if you see the warning, tighten those numbers
before touching the prompt.

== Tactic 9: verify with an empty case

If the commit list is empty, the `require-commits` stage stops the pipeline
with a hard-coded message before the summariser is loaded. Always
sanity-check what your prompt does on tiny inputs (one commit, one-word
messages) before declaring it "good enough".

== Historical anti-pattern

The retired single-model tool-calling system prompt read:

[source]
----
You are a developer assistant. You can call tools to fetch data from the
user's git repository, then summarise the results. When asked about recent
commits, call the `get_recent_commits` tool exactly once, then write a
short standup summary.
----

Pleasant English, but a structural mess for a 1B:

* Two tasks (call a tool *and* summarise) in one sentence.
* "Exactly once" — a constraint the model can't reliably honour.
* No example of a successful tool call.
* No exit condition (when does it know it has summarised "enough"?).

xref:explanation/negative-sample-2026-05-05.adoc[The 2026-05-05 negative
sample] documents what the model actually did with this. The two-model split
(Tactic 6) is the fix that went in.
