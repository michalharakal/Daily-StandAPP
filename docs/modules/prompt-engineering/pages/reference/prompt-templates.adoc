= Prompt Templates Reference
:toc: left
:icons: font

Every prompt currently used by the LLM module, with file paths so you
can verify (and iterate) against the live code.

== System prompts

The pipeline uses two models and therefore two system prompts: one that
tells Qwen3 to call the tool, one that frames the Llama 3.2 summariser.

=== Tool stage (`QwenCommitsStage.DEFAULT_SYSTEM_PROMPT`)

Source: `llm/src/jvmMain/kotlin/de/jug_da/standapp/llm/pipeline/QwenCommitsStage.kt`.

[source]
----
You are a git assistant. You must call the get_recent_commits tool to
look up commits; never answer from memory. Call the tool exactly once
with the days (integer) and, only if the user names one, the author
from the request.
----

~250 chars, one job: produce the call. `QwenChatTemplate` appends the
`# Tools` section with the tool schema after it (see
xref:reference/chat-templates.adoc[]). Override it per flow with
`qwenToolCall(systemPrompt = "…")`. Because the loop runs a single
round and the model's prose is discarded, the prompt does not need to
describe what to do with the result — that was the mistake of the
retired single-model prompt, which asked a 1B to fetch *and* summarise
(xref:explanation/negative-sample-2026-05-05.adoc[]).

=== Summary stage (`DefaultPrompts.SYSTEM` via `PromptSpec.system`)

Source: `standapp-ai-engine/src/commonMain/kotlin/dev/standapp/engine/control/PromptBuilder.kt`;
wired by `PromptStage` from the flow's `prompt { }` block.

[source]
----
You are a developer assistant that creates concise standup summaries
from Git commits.
----

Rendered as the Llama 3 system turn by `Llama3ChatTemplate`. Override
with `prompt { system = "…" }` in `standupFlow`.

=== `LLMService.SYSTEM_PROMPT`

Source: `llm/src/jvmMain/kotlin/de/jug_da/standapp/llm/LLMService.kt`.

[source]
----
You are a helpful assistant that creates concise standup summaries from
git commit data.
----

Constant on the `LLMService` companion. Used by `LlamaChatLLMService`
(the plain `LLMService` over the same Llama stage, for the benchmark,
`LLMSummarizer` and `STANDAPP_TINY_PROMPT=1`) — *not* by the CLI
pipeline, which goes through `PromptSpec.system` above.

== User prompts (engine layer)

Source: `standapp-ai-engine/src/commonMain/kotlin/dev/standapp/engine/control/PromptBuilder.kt`.

=== `DefaultPrompts.SUMMARY_USER`

[source,markdown,subs="-attributes"]
----
You are a developer assistant that creates daily standup summaries from
Git commits.

Given the following Git commits, produce a concise standup report with
exactly these three markdown headings:

## Yesterday
(Summarise work completed based on the commits)

## Today
(Infer planned work as a continuation, or state "Continue work on …")

## Blockers
(List any obstacles mentioned in commit messages, or "None")

Reference commit IDs where relevant. Be concise and actionable.

Commits:
{{commits}}
----

Used by `PromptType.SUMMARY` — the CLI default for `--format md` and
`--format text`. The structural skeleton trick (explicit headings +
parenthetical instructions per heading) is what makes a 3B reliable
here.

`\{\{commits\}\}` is replaced by `CommitFormatter.format(commits)` —
multi-line text, one commit per `--- ID / Author / Date / Message`
block. The commit list has already been through the flow's
`preprocess { }` (CLI default: `shortIds(7); firstMessageLine(120);
limit(60)`), which is what keeps prefill affordable on the 3B.

=== `DefaultPrompts.JSON_USER`

[source,markdown,subs="-attributes"]
----
You are a developer assistant that creates structured standup data from
Git commits.

Given the following Git commits, produce a JSON object with this exact
structure:
{
  "date": "<YYYY-MM-DD of the most recent commit>",
  "author": "<primary author name>",
  "categories": [
    {
      "name": "<category, e.g. Bug Fixes, Features, Refactoring, …>",
      "commits": [
        {
          "id": "<commit hash from input>",
          "summary": "<one-line summary>",
          "status": "done | in-progress | unknown"
        }
      ]
    }
  ],
  "blockers": ["<any obstacles, or empty array>"]
}

Rules:
- Output ONLY valid JSON, no markdown fences, no extra text.
- Every commit ID must come from the input — do not invent IDs.
- Group commits into logical categories.
- If there are multiple authors, use the most frequent as "author".

Commits:
{{commits}}
----

Used by `PromptType.JSON` — selected by `--format json`, where the
output is parsed strictly, retried once on invalid JSON
(`retryOnInvalid(maxAttempts = 2)`) and parsed leniently on the last
attempt. The `:benchmark` module exercises it as well.

=== `DefaultPrompts.SYSTEM`

[source]
----
You are a developer assistant that creates concise standup summaries
from Git commits.
----

Engine-layer default system prompt; this *is* the summariser's system
turn in the CLI pipeline (see "Summary stage" above).

== Tool-stage user prompt

Source: `llm/src/jvmMain/kotlin/de/jug_da/standapp/llm/pipeline/QwenCommitsStage.kt`,
`userPrompt(request)`.

[source]
----
Fetch the git commits from the last N day(s)[ by author "…"] using
get_recent_commits. Pass days=N as a number[ and author="…"].
----

Built from the `StandupRequest` (`--days`, optional `--author`). The
bracketed clauses appear only when an author is given. It restates the
argument values and their type on purpose: a 0.6B model copies what it
sees, and `days` as a JSON string would fail schema validation. Not
overridable from the DSL today — change the system prompt or the tool
description instead.

== Tool descriptions (rendered into system message)

Source: `llm/src/jvmMain/kotlin/de/jug_da/standapp/llm/GitTools.kt`,
`RecordingGitCommitsTool.definition`.

[source,json]
----
{
  "name": "get_recent_commits",
  "description": "List the git commits of the repository from the last N days. Returns the number of commits found; the commit details are handed to the summariser.",
  "parameters": {
    "type": "object",
    "properties": {
      "days": {
        "type": "integer",
        "description": "Number of days to look back from now (positive integer, e.g. 7)."
      },
      "author": {
        "type": "string",
        "description": "Optional author name filter. Omit for all authors."
      }
    },
    "required": ["days"]
  }
}
----

The `description` text on each parameter is what the model uses to
decide what value to put there — keep it specific and actionable, not
just a type restatement. `QwenChatTemplate` renders this object inside
`{"type":"function","function":{…}}` on one line in the `<tools>` block;
`ToolCallValidator` checks the model's `arguments` against `parameters`
before the tool runs. The description deliberately says the details go
to the summariser: the tool's string result is only an acknowledgement,
the structured list is recorded on the tool object.
