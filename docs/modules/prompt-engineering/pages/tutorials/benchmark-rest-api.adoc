= Exercise: Benchmark with an OpenAI-Compatible Server (Ollama / LM Studio)
:toc: left
:icons: font

**Engine:** RestApiLLMService (HTTP client) +
**Goal:** run the benchmark suite against a local or remote
OpenAI-compatible inference server. **Time:** ~10–30 min depending on
the model + hardware.

This exercise gets you cross-checking SKAINET's embedded results
against a different runtime — Ollama, LM Studio, llama.cpp's HTTP
server, vLLM, or even OpenAI's hosted API. Same `LLMService`
interface, very different runtime.

== Prerequisites

[cols="1,3"]
|===
|Need |Why

|JDK 21+
|Same as for SKAINET — the benchmark module compiles against JDK 25
toolchain but runs on 21+.

|One of these inference servers
|Ollama (`brew install ollama`, `apt install ollama`, or
`curl -fsSL https://ollama.com/install.sh \| sh`); +
LM Studio (download from https://lmstudio.ai); +
llama.cpp's `llama-server`; +
or any OpenAI-compatible HTTP endpoint.

|Reachable from this machine
|If the server runs on a peer (LAN), make sure it binds to 0.0.0.0 not
just 127.0.0.1. From this machine: `curl http://server:1234/v1/models`
should return JSON.
|===

== For Java developers — env vars vs Gradle properties

This exercise leans on environment variables (`BENCH_LOCAL_URL=…`)
rather than Gradle properties (`-P…`). The convention in this repo:

* **Env vars (`BENCH_*`, `MCP_*`)** configure benchmark *runtime*
  behaviour — which backends to test, where they live, what model name
  to use.
* **Gradle properties (`-P…`)** configure *build-time* behaviour —
  which optional source sets to compile in (Deliverance, qxotic).

You set env vars the standard way for your shell:

[source,bash]
----
# inline (one command)
BENCH_LOCAL_URL=http://localhost:1234/v1 ./gradlew :benchmark:jvmRun

# or for the whole shell session
export BENCH_LOCAL_URL=http://localhost:1234/v1
./gradlew :benchmark:jvmRun
----

== Steps

=== 1. Start an inference server and pull a model

Pick one of:

==== Ollama (CLI)

[source,bash]
----
# install ollama, then in a separate terminal:
ollama serve

# in your main terminal:
ollama pull llama3.2:3b           # ~2 GB
# verify it's reachable:
curl http://localhost:11434/v1/models
----

==== LM Studio (GUI)

. Open LM Studio.
. Search for and download "Llama 3.2 3B Instruct" (or any other model).
. Open the "Developer" / "Local Server" tab.
. Click *Start Server*. Default port is `1234`.
. Confirm: `curl http://localhost:1234/v1/models` should return JSON.

If LM Studio is on a different machine, toggle "Serve on Local
Network" / "CORS" so it binds to `0.0.0.0`, and use that machine's IP
in the next step.

=== 2. Run the benchmark with REST_API only

For Ollama:

[source,bash]
----
BENCH_BACKENDS=REST_API \
BENCH_LOCAL_URL=http://localhost:11434/v1 \
BENCH_LOCAL_MODEL=llama3.2:3b \
BENCH_RUNS=3 \
    ./gradlew :benchmark:jvmRun --console=plain
----

For LM Studio (note port and model-name format differ):

[source,bash]
----
BENCH_BACKENDS=REST_API \
BENCH_LOCAL_URL=http://localhost:1234/v1 \
BENCH_LOCAL_MODEL=llama-3.2-3b-instruct \
BENCH_RUNS=3 \
    ./gradlew :benchmark:jvmRun --console=plain
----

For a remote LM Studio at `192.168.3.168`:

[source,bash]
----
BENCH_BACKENDS=REST_API \
BENCH_LOCAL_URL=http://192.168.3.168:1234/v1 \
BENCH_LOCAL_MODEL=llama-3.2-3b-instruct \
BENCH_RUNS=3 \
    ./gradlew :benchmark:jvmRun --console=plain
----

`BENCH_LOCAL_API_KEY` is also available if your endpoint demands a
Bearer token; safe to leave unset for Ollama and LM Studio.

=== 3. Inspect the report

[source,bash]
----
cat benchmark-results/benchmark-report.md | head -40
----

== What you should see

A `REST_API (local)` row in the comparison table. Compared to SKAINET
(if you ran that exercise first):

* On a 3B model the **auto pass rate** typically rises to 0.85+ (vs
  ~0.65 for the embedded 1B). Larger model, more capacity for
  structured output.
* **Latency p50** depends entirely on the server's hardware. A 3B model
  on CPU is typically 8–20 s per case; on a 3060+ GPU, 1–3 s.
* **Determinism** drops if the server doesn't honour the same
  temperature you pass — Ollama defaults to non-deterministic sampling
  even at `temp=0.6`. Check the server's docs.

== Stretch goals

* Add a *cloud baseline* — set `BENCH_CLOUD_URL`, `BENCH_CLOUD_MODEL`,
  `BENCH_CLOUD_API_KEY` (or `OPENAI_API_KEY`) to compare against
  GPT-4o-mini. The report will produce a "Cloud vs Local Delta
  Analysis" section.
* Run **both SKAINET and REST_API** in one invocation
  (`BENCH_BACKENDS=SKAINET,REST_API`) and read the side-by-side
  comparison.
* Try a smaller server-side model (e.g. Ollama's `qwen2.5:1.5b`) and
  see how the auto pass rate changes vs throughput.

== When this tutorial breaks

* `Connection refused` → server isn't running, wrong port, or bound to
  loopback only. Test `curl <BENCH_LOCAL_URL>/models` from this
  machine.
* `404 model not found` → `BENCH_LOCAL_MODEL` doesn't match an
  installed model id. List with
  `curl <BENCH_LOCAL_URL>/models \| jq`.
* `connect timed out` (long delay) → host unreachable. From a
  command-line peer, `ping` and `nc -zv host port` to confirm.
* `read timed out` → the model is loading on first call. Re-run; the
  second call should succeed once the server has the model resident.
