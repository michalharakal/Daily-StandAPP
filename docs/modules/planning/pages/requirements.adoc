= Requirements: Upgrade, Pipeline DSL, E2E CLI, Benchmark
:navtitle: Requirements

Requirements for the July 2026 iteration. Each requirement has a stable ID
(`REQ-nn`) referenced by the xref:design.adoc[design document] (`DES-nn`) and
the xref:tasks.adoc[implementation tasks] (`T-nn`).

== Scope

Four work streams, in order:

. Bring all upstream dependencies to their latest released versions.
. Express pre- and post-processing as a typed Kotlin pipeline DSL
  ("everything as code", the SKaiNET philosophy).
. Finish the end-to-end CLI: git directory in, standup summary out.
. Run the full benchmark across all local inference engines and publish the
  report.

=== Pipeline DSL ("everything as code")

[cols="1,5a", options="header"]
|===
| ID | Requirement

| REQ-10
| A typed Kotlin pipeline DSL in `:standapp-ai-engine` composes the stages
`preprocess → prompt → infer → postprocess` over the types
`List<CommitInfo> → prompt String → raw String → StandupSummary → ScoredResult`.
Stage configuration is plain Kotlin code (builder lambdas with `@DslMarker`),
no configuration files.

| REQ-11
| The inference stage is injected as a `suspend (system: String, user: String) -> String`
function. `:standapp-ai-engine` gains no dependency on `:llm`, `:data`, or any
inference library.

| REQ-12
| The prompt stage supports both existing prompt types (`SUMMARY` markdown,
`JSON`) and swapping between them is a one-line change in pipeline code.
Prompt bytes produced for a given input are identical to the current
`PromptBuilder`/`CommitFormatter` output.

| REQ-13
| Post-processing parses LLM output into the existing `StandupSummary` model:
markdown output via the `## Yesterday` / `## Today` / `## Blockers` headings,
JSON output via the schema already validated by `QualityScorer`. Strict
parsing failures raise a typed exception; lenient mode falls back to the raw
text. An opt-in retry stage re-runs inference when strict parsing fails.

| REQ-14
| Quality scoring (`QualityScorer`) is available as an opt-in pipeline stage;
the pipeline derives the valid commit-ID set from its own input.

| REQ-15
| CLI and benchmark run LLM interactions through the same pipeline
implementation (single code path).
|===

=== End-to-end CLI

[cols="1,5a", options="header"]
|===
| ID | Requirement

| REQ-20
| The CLI accepts: `--repo/-r <dir>`, `--author/-a <name>`, `--days/-d <n>`,
`--since <YYYY-MM-DD>`, `--until <YYYY-MM-DD>`, `--format md\|json\|text`,
`--backend <name>`, `--model <path>`, `--output <file>`, `--score`,
`--max-tokens <n>`, `--temperature <f>`, `--tool-calling`, `--help/-h`.
`--since`/`--until` take precedence over `--days`.

| REQ-21
| Output formats: `md` (markdown summary), `json` (serialized `ScoredResult`),
`text` (plain sections). Output goes to stdout or to `--output <file>`. When
machine-readable output is requested, token streaming does not pollute stdout.

| REQ-22
| `--score` prints a check-by-check quality report to stderr.

| REQ-23
| Exit codes: `0` success, `2` usage error, `3` git error or no commits found,
`4` LLM/backend error, `5` validation failure (failed quality checks or
exhausted parse retries).

| REQ-24
| `--backend` and `--model` override the `MCP_LLM_BACKEND` /
`MCP_LLM_MODEL_PATH` environment variables; the env vars keep working.
`--tool-calling` supersedes `STANDAPP_TOOL_CALLING=1` (env kept as fallback).
|===

=== Benchmark

[cols="1,5a", options="header"]
|===
| ID | Requirement

| REQ-30
| A full benchmark run is executed across all local engines — SKAINET
(embedded GGUF), REST_API (local Ollama), DELIVERANCE, QXOTIC — over all 15
cases, both prompt types, 5 measured runs plus 1 warm-up each.

| REQ-31
| The per-run timeout is configurable via `BENCH_TIMEOUT_MS` (the fixed 30 s

| REQ-32

`benchmark-results/benchmark-results.csv`, plus a written comparison summary.

== Non-functional requirements

[cols="1,5a", options="header"]
|===
| ID | Requirement

| REQ-40
| Privacy first: the default flow performs no network calls; all inference is
local. (REST_API remains an explicit opt-in.)

`CommitFormatterTest`, `MetricsTest`, `LLMSummarizerStreamTest`,
`GitClientTest`. `CommitFormatter` output format and `QualityScorer` semantics
are frozen.

| REQ-42
| Each upgrade batch is an independently revertible commit with a verification
gate that passed before commit.

| REQ-43
| Benchmark results remain comparable with earlier runs: identical prompts,
identical scoring, same case files.

| REQ-44
| The code stays readable as talk-demo material: the DSL favours small,
explicit types over generality; no new CLI argument-parsing dependency.

| REQ-45
| New logic (parser, pipeline, CLI argument parsing) is covered by unit tests
runnable without a model download.

== September 2026 iteration: SKaiNET 0.53 two-model pipeline

Requirements for the second iteration (started 2026-09-02): latest SKaiNET
releases, function calling with a small model, and the standup flow expressed
as a SKaiNET data pipeline. Referenced by xref:design.adoc[DES-08..DES-10] and
xref:tasks.adoc[T-16..T-25].

[cols="1,5a", options="header"]
|===
| ID | Requirement

| REQ-50
| SKaiNET core and SKaiNET-transformers are upgraded to the latest published
release, 0.53.0 (Maven Central), consumed through their BOMs. Kotlin follows
the upstream toolchain (2.4.10), Ktor the data-source module (3.5.2). A local
`../SKaiNET-transformers` checkout is opt-in (`-PuseLocalTransformers=true`),
never implicit, so a plain checkout and CI resolve the same dependency graph.

| REQ-51
| Two local models in sequence: Qwen3-0.6B (Q8_0) turns the request into a
`get_recent_commits` function call whose structured result feeds
Llama-3.2-3B-Instruct (Q4_K_M) for summarisation. The flow is declared as a
SKaiNET data pipeline (`sk.ainet.data.source.DataPipeline`) through an
extendable app-level DSL: every step is a `PipelineStage`, custom transforms,
tools and generation stages can be plugged in without modifying the built-ins.
If the tool model produces no valid call the pipeline falls back to direct git
access and reports it — the CLI always delivers a summary.

| REQ-52
| Models are not bundled. Both GGUFs are resolved on first run through the
SKaiNET `hf://` data-source resolver into a local cache
(`STANDAPP_MODEL_CACHE_DIR`, default `~/.cache/standapp/models`) and reused
afterwards; local files can be supplied via CLI flags or
`STANDAPP_QWEN_MODEL_PATH` / `STANDAPP_LLAMA_MODEL_PATH` (`MCP_LLM_MODEL_PATH`
stays a legacy alias for the summariser). `STANDAPP_OFFLINE=1` forbids network
access. Privacy stays intact: after the download no network call is made.

| REQ-53
| The single-model legacy paths are replaced, not kept alongside: embedded
Llama-1B JAR resource, `prepareModel`/`download-model.py`, `EmbeddedModelLoader`,
`SKaiNetLLMService`, `ToolCallingLLMService`, `--tool-calling`. `REST_API`,
`:mcp-server`, `:benchmark` and `cloud-api/*` keep compiling; `LLMService`
remains the plain prompt-in/text-out contract for them.

| REQ-54
| CI and Docker build with the JDK 25 toolchain the modules request; the
container's temp directory allows the native SKaiNET kernel library to load.

| REQ-55
| README, CLAUDE.md, arc42 and prompt-engineering docs describe the two-model
pipeline; superseded decisions are marked as such; the task table in
xref:tasks.adoc[] tracks progress with verification gates.
|===
