= PRD: SKaiNET Core — LLM-Ready Engine
:navtitle: PRD — SKaiNET core

Product requirements for the SKaiNET core repository
(https://github.com/SKaiNET-developers/SKaiNET[SKaiNET-developers/SKaiNET],
artifacts `sk.ainet:skainet-bom` + `sk.ainet.core:*`) within the upstream
performance program. Companion documents:
xref:prd-skainet-transformers.adoc[PRD — SKaiNET-transformers] and
xref:integration-release-plan.adoc[Integration & Release plan].

== Goal

Make the core engine's CPU kernels, benchmark truth, and compiler stack ready
to serve LLM decode/prefill workloads at Deliverance-class speed and beyond —
without the core repo owning any transformer/LLM logic itself. Core provides
kernels, tensor-op contracts, the DAG/compile stack, and (via the program's
architecture decision) the path to a single execution IR executed either
in-process or through MLIR → IREE.

== Non-goals

* Transformer/LLM model logic (attention modules, KV caches, chat templates,
  agent loop) — that is SKaiNET-transformers territory.
* Hand-written GPU kernels (Metal/CUDA) — superseded by the IREE compiler
  track per program decision.
* Sampling algorithms — live in the transformers repo (`llm-core`).

== Current state (verified 2026-07-23)

* Kernel SPI in `skainet-backends/skainet-backend-api`
  (`sk/ainet/backend/api/kernel/`) is a true GEMM interface:
  `matmul(a, …, b, …, out, …, m, n, k)` computing `C(m,n) = A(m,k)·B(k,n)`
  row-major with strides. Panama SIMD implementations exist in
  `skainet-backend-cpu` for FP32, BF16, Q8_0, Q4_0, Q4_K, Q5_0, Q5_1, Q5_K,
  Q6_K with scalar fallbacks; `skainet-backend-native-cpu` adds C kernels via
  FFM. The API docs state "no fused-accumulate kernel is in scope yet."
* Benchmark infrastructure exists: `skainet-backends/benchmarks/jvm-cpu-jmh`
  (JMH: `KernelMatmulBench`, `QuantizedMatmulBench`, …), an
  `engine-benchmarks.yml` CI workflow, and OpenBenchmarking profiles — but no
  LLM-shaped scenarios (decode GEMV, prefill GEMM, lm_head).
* Compile stack: `skainet-lang-dag` (graph DSL + `TraceToGraphProgram`),
  `skainet-compile-dag` (`ComputeGraph`, executor, `LLMFusedOpHandlers`),
  `skainet-compile-opt` (fusion/DCE/transpose-elimination passes),
  `skainet-compile-hlo` (**StableHLO/MLIR export**: `StableHloConverter`,
  `dag2hlo`, `MlirValidator`), `skainet-io-iree-params` (IREE `.irpa` weight
  archives). No IREE compiler/runtime integration in core itself; the
  embedded track invokes `iree-compile`/`iree-run-module` via shell.
* Consumer-observed behavior (from the transformers side): the production
  decode path is eager DIRECT mode; ~1.8 tok/s decode on Llama 3.2 1B Q8_0,
  M-series CPU.

== Success metrics

* CORE-1 scenario suite runs in CI on every release; baselines in release notes.
* Q8_0 prefill-shape GEMM ≥ 3× m×GEMV (CORE-2).
* A decoder graph compiles StableHLO → IREE CPU-HAL and runs with greedy
  parity in CI (CORE-5 + CORE-6).
* No breaking kernel-SPI change within the release train (contract CT-A).
